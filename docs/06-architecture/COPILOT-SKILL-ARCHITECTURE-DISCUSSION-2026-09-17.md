# Copilot 问题处理与输出 Skill 化讨论稿

## 1. 本轮结论与范围

建议推进 Skill 化，把可复用的问题处理方法、必要证据要求和表达规则从散落的 Prompt 中提炼出来；同时改进自由问题路由与行为评测。**收益来自方法集中维护、按需加载、明确合同和持续评测，不能由“包装成 Skill”本身保证。**

本轮是用户要求的研究与讨论，不改变运行代码、模型配置、工具权限、既有验收结论或真实 API 接入范围，也不安装或创建可执行 Skill。拟议方案经过讨论后，再按 PRD → Feature Spec → Tickets 进入实现。

本轮 Write Set：本文、[一手行业证据](../01-research/COPILOT-SKILL-INDUSTRY-EVIDENCE-2026-09-17.md)、[真实接入索引](../04-specs/features/copilot-real-context-integration/README.md)中的讨论入口。现有工作区修改全部保留。本文的代码判断针对 2026-09-17 当前工作树；不把它表述为某个已提交版本。

依据包括：[项目简报](../00-project/PROJECT-BRIEF.md)、[决策账本](../00-project/DECISION-LEDGER.md)中 D-120、D-152、D-155～D-164、[真实接入 PRD](../04-specs/features/classin-test-integration/PRD.md)、[Copilot 真实 Context Spec](../04-specs/features/copilot-real-context-integration/FEATURE-SPEC.md)及实现。既有[六部分分解](./COURSE-PRODUCTION-SIX-PART-DECOMPOSITION.md)已经区分 Skill、Tool、Agent 与 Rule Validator；其中 SkillExecutor 是设计方向，不是当前 Copilot 已经启用的模块。

## 2. 当前究竟是怎样工作的

### 2.1 已核实的实际链路

```text
教师输入 / 点击推荐
  → 前端判断查询或消息草稿意图
  → capture(query, focusRefs, referenceId)
  → 服务端关键词首个命中路由 + 授权对象定位 + 真实 API 读取
  → Context 投影 + 通用问题规则 + 可选草稿规则
  → DeepSeek 回答
      ↳ 可以调用 read_classin_context 补查，再进入同一服务端路由
  → 共享 Markdown 渲染
  → 教师审阅 → 事实版本/身份校验 → 当前本地模拟发送
```

首轮取数先于 DeepSeek 判断。当前不是全部由模型先选择 19 个独立业务工具再执行。合同里确有 19 个逻辑工具 ID，但模型可调用的 ClassIn 读取入口是 `read_classin_context`。Tool 也不因为被 Skill 使用就自动变成 MCP Tool；MCP 是工具暴露协议，Skill 是使用方法，API/Adapter 是实际数据访问实现。

对应位置：[提交编排](../../src/features/workbuddy-im-assistance/ImSidecarAgentSurface.tsx)、[真实 Context Adapter](../../src/features/classin-test/classin-test-adapters.ts)、[服务端路由](../../server/classin-test-middleware.ts)、[模型补查工具](../../runtime/harness/classin-read-tool.mjs)、[逻辑工具合同](../../src/contracts/classin-test/copilot-context.ts)。

### 2.2 硬编码与 Prompt 盘点

| 环节 | 当前证据 | 判断及拟议归属 |
| --- | --- | --- |
| 自由问题识别 | `routeQuestion` 按顺序运行正则，只返回一个 questionId；部分回复条件包含固定姓名字面量 | 语义判断适合路由方法；合法对象、问题范围、执行预算由代码核验。需支持复合问题与澄清。 |
| 具体对象和时间范围 | 讲次/题号解析、活动名匹配、种类关键词过滤；最多 4 个 focus；F1 摘要取数固定采用最近 5 天 | 时间意图可以由模型解释；绝对日期换算、唯一对象绑定、范围上限继续代码。当前 UI 模板仍有“两天”，须将请求范围与实际覆盖分开。 |
| P01–P10 推荐 | `projectDynamics` 根据发布时间、过程状态等生成推荐及固定 teacherRequest | 触发条件、空态、排序和去重保留代码；推荐携带稳定任务 ID，回答方法复用 Skill。避免生成一句问题后再猜它是什么任务。 |
| 问题回答方法 | `buildGeneralQuestionRequest` 按关键词添加出勤、录播、逐题、资料、学情、群聊等说明 | 最适合按问题族提取：必须读取什么、如何解释、哪些推断不成立。 |
| 通用表达与格式 | 系统 Prompt、普通问题 Prompt、草稿 Prompt 都有表格规则；多个地方要求结论、日期和简洁性 | 建立单一维护源。常驻少量事实底线，输出表达方法可复用，避免三处同步修改。 |
| 消息目的与正文抽取 | `none/suggest/draft`、正文标记与正则清理 | 受众/语气/改写方法可提取；交付状态、教师确认、正文一致性与发送校验继续代码。结构化交付意图是后续可评估方向。 |
| 事实与业务解释混合 | Context 投影里把业务数字、说明和回答禁令拼成文本，并按 200 字符分片 | 逐步把事实、派生口径、缺失状态和表达方法分开。事实保留可核对字段；Skill 不拥有真实业务值。 |
| 上下文预算 | envelope 对单项/消息限长，总串长以 11,600 字符为裁剪目标，包含增强后的 teacherRequest；超过时删消息/证据项并加覆盖说明 | 长 Prompt 与证据竞争容量是可见问题。按需加载需要统一预算和必要证据优先级，不能仅把说明换个通道塞入。 |
| 取数回执 | `requestedToolIds` 与 `executedToolIds` 均直接赋值为 `supplement.route.tools` | 当前只能证明逻辑映射，不能独立证明模型计划和逐工具执行。必须区分计划、实际调用、成功/失败/缓存/部分结果。 |
| 字体、表格和消息展示 | `RichTextContent` 共用于 AI 和聊天；CSS 已负责表头及首列字重 | 保留在共享 Design System；Skill 决定信息如何组织，组件保证视觉呈现。 |

### 2.3 路由只读验证

本轮从当前文件提取原始 `routeQuestion`，使用 TypeScript 转译后在内存运行；姓名参数为合成标签“示例学生”。没有读取真实学生数据、调用业务 API 或向模型提问。这些结果证明分类器的行为，不等于完整 Agent 最终一定回答错误。

| 输入 | 当前返回 | 暴露的局限 |
| --- | --- | --- |
| 这节录播课程大家分别学到哪了？ | A1 / `read_course_progress` | 录播个人进度被更早的课程总进度规则截获，应优先识别 B3。 |
| 请总结示例学生本周的学习情况，并列出到课记录。 | B1 / `read_class_attendance` | 出勤关键词覆盖个人学情主任务；应保留 D1 与其出勤证据需求。 |
| 最近哪些题做错的人多？作业批阅到哪了？ | C2 / `read_homework_students` | 仅表达批阅子问题，没有表达 C5 逐题分析意图。 |
| 我们班下一节课的安排是什么，学生一共有多少人？ | A2 / `list_course_activities` | 只记录排期任务，未显式表达班级人数意图；不能仅凭回执判断人数证据是否够用。 |
| 把刚才的内容整理成一条消息 | E5 / `reuse_conversation_artifact` | 已知正例正常；迁移须保留这些有效路径。 |

因此，已验收的标准问法通过，与任意改写及组合问法稳定通过是两件事。当前证据不足以估计全部真实问法的错误率，也不改变既有样本验收结论。

## 3. 行业证据如何用于本项目

[一手研究](../01-research/COPILOT-SKILL-INDUSTRY-EVIDENCE-2026-09-17.md)核查了 Agent Skills 开放格式、官方集成指南、Anthropic 工程与评测、LangGraph 路由、MCP 工具合同。可采纳的原则是：

- Skill 封装说明及配套资源，先展示描述、按需加载正文；加载说明不等于新建一个 Agent，也不必为每份说明增加一次独立答案生成。[Agent Skills 集成指南](https://agentskills.io/client-implementation/adding-skills-support)
- 固定流程与模型决策可组合。模型可以选择限定的路由结果，程序负责验证与执行；不必为此更换现有框架。[LangGraph 官方路由示例](https://docs.langchain.com/oss/python/langgraph/workflows-agents#routing)
- 从真实失败建立评测，再逐步增加方法。评测应覆盖反例与重复运行；不能只检查有没有某个标题、某句 Prompt 或某次特定工具顺序。[Anthropic 评测实践](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

以下分层、问题族数量和迁移次序是本项目设计建议，不是行业标准规定。

## 4. 建议的分层

| 层次 | 职责 | 使用方式 |
| --- | --- | --- |
| 常驻规则 | 真实证据、对象隔离、未知不补造、事实与推断分开、教师审批边界 | 少量且强制保留；不能依赖模型是否想起调用某个 Skill。 |
| 路由方法 | 识别问题族、目标对象、时间、复合意图、查询或消息目的 | 固定入口直接提供任务标识；自由输入由模型选择，结果经 Schema 与业务校验。 |
| 问题族 Skill | 必要证据、可选证据、业务解释、回答结构、正反例 | 主 Agent 按需使用，可组合；共用事实合同。 |
| 通用回答 Skill | 没有专门方法时如何澄清、基于可用证据回答、表达能力边界 | 受控兜底；不能用通用常识填补真实业务数据。 |
| 输出表达 Skill | 选择段落/列表/表格；组织重点、受众和引用 | 宿主保证相关输出规范进入上下文，不依赖可选触发；表格选择保留模型判断。 |
| Tool、Validator、Renderer | 真实取数、计算、字段合同、执行校验、视觉和发送前后的一致性 | 继续确定性代码；Skill 不能改写工具授权和业务事实。 |

“路由 Skill”是解释如何识别问题的方法；**运行时路由器**是保证这一步发生、接收结果并执行下一步的程序。无需再增加一个路由器来猜是否调用路由 Skill。

对于“格式 Skill”，也不建议额外建立一个模型把每次答案重写一遍：这会增加延迟和事实漂移机会。先在同一主 Agent 中使用共享表达规则；确有格式失败时，再评估有边界的修复步骤。

### 4.1 按业务方法划分，不默认每题一 Skill

以下为候选主归属，每个已验收 questionId 出现一次。组合问题可复用其他问题族的方法，但主归属应唯一，以便发现遗漏和重复维护。

| 候选问题族 | 主归属题号 | 方法重点 |
| --- | --- | --- |
| 课程与安排 | A1、A2、A3、A4 | 课程、课堂、单元与活动关系；排期和人数口径；不合成混合进度。 |
| 出勤与学习参与 | B1、B2、B3 | 实时/历史出勤、录播分别使用合同；分母、状态、时长和缺失不能混用。 |
| 作业与测验状态 | C1、C2 | 要求、截止、分配、提交、批阅分开；未交与未批不同。 |
| 题目分析 | C5 | 完整题面、有效判定分母、错误/部分正确；不推断个体错因。 |
| 课堂与资料内容 | E1、E2、E3 | 入口可用与正文可读分开；转写、笔记、AI 分析、资料正文分源。 |
| 学情汇总 | D1、D2、E4 | 个体/班级、时间窗、覆盖、已完成/未完成/未来安排；组合出勤和活动证据。 |
| 群聊理解与回复 | F1、F2、F3 | 原消息、前后文、日期和对象；已有回复查重；F2 复用完整题面与验算方法。 |
| 消息与家长草稿 | D5、E5 | 改写已取得事实、受众和目的、保留关键限制；复用学情方法，不增加发送权限。 |

数量不是交付指标。例如出勤与录播差异若在评测中导致混用，可以拆成独立 Skill；若 E1 只是入口检索，保持为轻量规则也可。先按共享业务方法组织，再根据错误和维护成本调整。

四个业务环节与 P01–P10 继续沿用既有[覆盖矩阵](../04-specs/features/copilot-real-context-integration/TEACHING-DYNAMICS-COVERAGE.md)：P01 复用课程，P02 复用排期与草稿，P03 复用实时出勤边界，P04 复用配套活动/任务，P05/P06 复用提交状态，P07 复用逐题分析，P08 复用课堂回顾，P09 复用班级汇总，P10 复用个人汇总。推荐触发、无任务占位和去重仍由代码维护；Skill 化不会让缺失的实时接口变得可用。

### 4.2 以用户截图的录播回答为例

1. 识别为录播学习参与，绑定当前录播对象，而不是课程总进度。
2. 使用录播方法：核对分配人数、成员状态、接口进度、学习时长、开放时间和评分设置。必要证据缺失则列出限制，不能把“未知”写成“未开始”。
3. 使用表达规范：先给总体结论；简短元信息可用“项目/内容”表；多人相同字段采用“学生/状态/进度/时长”表。内容很少时允许段落，不为凑表格重复信息。
4. 数字与状态来源经代码核验；表头与第一列由组件强调；同一正文在 AI 区和群聊区渲染。

现有“2 个对象或 4 项属性必须用表格、元信息与成员进度必须拆成两表”是当前实现采用的启发式，不是普遍正确的标准。建议改为可评测的场景示例和偏好，结合信息密度、长文本比例、窄窗口可读性判断；保留必要的结构约束。

## 5. 技术方案讨论

### 5.1 Runtime 能力与当前启用状态

启动脚本固定 `@deepseek-ai/dsh@0.1.1-rc.2`。仓库历史结构盘点记录的上游固定提交 `b150a551b8d465e31e418e1b2eaf5e79bbb7d28e` 中，已有 `skill(name)`、目录描述与延迟正文加载。它的正文保留在工具历史里；资源链接不会自动读取，正文修改也没有版本通知协议。[固定提交的 Skill 工具说明](https://github.com/deepseek-ai/deepseek-harness/blob/b150a551b8d465e31e418e1b2eaf5e79bbb7d28e/packages/skill/tool-skill/README.md)

同一提交的文件 Provider 支持显式自定义目录，并可以关闭默认个人/项目目录发现；只发现一层 Skill 包。[固定提交的文件 Provider](https://github.com/deepseek-ai/deepseek-harness/blob/b150a551b8d465e31e418e1b2eaf5e79bbb7d28e/packages/skill/skill-filesystem/README.md)

但当前 [teachingToolGuard](../../runtime/harness/teaching-tools.mjs) 只放行教学草稿、解题图片和授权 ClassIn 补查，`skill` 不在其中；本轮没有发现项目显式配置的产品 Skill 目录。**上游存在能力，不等于当前 Copilot 已启用，也不等于已核验运行包与该源码完全一致。** 本轮仅静态检查，没有修改权限或实际加载 Skill。实施前需单独验证当前包的加载、资源可读性和会话行为。

建议优先复用现有 Harness 的能力，以受控产品目录或受控 Provider 提供方法。产品 Skills 不应自动继承开发者个人电脑上的 Skills；也不需要为读取受信方法开放通用 Shell 或任意文件访问。

### 5.2 两种入口、一个主 Agent

固定入口传入稳定的推荐 ID/questionId 和对象引用。自由问题产生有边界的计划，例如问题族列表、对象线索、时间范围、所需证据和输出意图；字段由本地 Schema 校验，对象 ID 再由授权目录解析核验。输入中有多个任务就保留多个任务，避免首个关键词吞掉其余部分。

遇到对象歧义，先尝试当前会话已确认对象；仍不唯一才向老师澄清。不要把模型自报“置信度 90%”直接当可靠度。路由失效时保留明确的可恢复状态；不能悄悄改用无关通用回答掩盖失败。

工具映射使用同一注册表，先复用已有业务读取服务，不因增加 Skill 再复制一套 API 请求逻辑。模型补查时也应保留已验证的任务身份，避免每次绕回自然语言正则重新猜题。

通用规则、主问题族和输出方法都可以在同一 Agent 会话中组合。逻辑分层不等于固定五次串行模型调用；实际工具轮数、Token 和延迟需测量。

### 5.3 Skill 包与运行合同

每个问题族包拟包含：适用/不适用条件、必要输入、必要与可选证据、读取与解释方法、缺失分支、输出示例、反例、关联评测。`SKILL.md` 用于方法说明，具体业务字段以已有工具合同为唯一事实源，避免多份字段清单漂移。

宿主另维护 Skill 的版本/内容哈希、依赖和允许的能力集合、结构化计划 Schema、评测版本。这些是本项目治理字段，不是 Agent Skills 标准要求的统一执行协议。

每个 Run 固定使用的方法版本，并记录：选择/加载来源、任务计划、实际工具执行及结果状态、证据引用和覆盖、回答校验、教师评价。加载了 Skill 不代表相关业务已经成功执行。Skill 更新面向后续 Run 生效，已生成并审阅的消息保留原版本，不能静默改写。

业务证据保持数据身份，尤其聊天正文、转写、资料中的指令不得被当成 Skill。权限、事实新鲜度、身份与发送审批继续强制执行；方法冲突遵循项目锁定业务规则，并在工程评测中报出，不能让模型随意选择更宽松规则。

### 5.4 输出方案：先集中规范，再评估强结构

第一步仍沿用 Markdown 与共享 `RichTextContent`，集中回答和格式方法。表格列结构、长文本换行、列表/引用/链接、发送前后显示做程序和浏览器回归。模型决定适合的表达，组件保证字重、边距和溢出行为。

如果对照评测仍有稳定出现的格式或数字转写问题，再评估结构化 AnswerDocument：段落、列表、表格等块附证据引用，由代码校验、填充确定数字并序列化为相同消息正文。它属于候选后续方案，不是本轮要求全面改写输出协议。

合法 JSON 不能保证业务正确；MCP 工具输出 Schema 也不等于模型生成必然服从 Schema。当前模型网关对受约束输出的兼容性尚未在本轮验证，不能作为既定条件。先保留本地验证与失败恢复。

## 6. 如何证明质量提高

### 6.1 比较基线

以当前已验收版本为基线，冻结同一问题、同一真实 API 回放快照、模型和采样参数。历史真实回放明确标记为回放，私有样本放被忽略的受限目录；运行 Demo 的无任务场景仍只使用真实 API，不能为展示补造业务数据。

建议分组对照：A 当前版本；B 仅集中重复 Prompt；C 增加按需 Skill 加载；D 在 C 上增加语义路由与执行校验。这样才能区分收益来自规则整理、Skill 选择还是路由改进，避免将所有改动后的提升都归给 Skill 包装。

### 6.2 样本与成功标准

| 维度 | 拟议检查 |
| --- | --- |
| 范围完整 | 21 类问题与 P01–P10 全部有映射，每个主方法归属唯一；范围覆盖不等于开放问法成功率。 |
| 问法变化 | 每类原题加至少两种改写；再加上述路由反例、复合问题、含糊对象、前文承接、跨时间窗。 |
| 数据边界 | 真正为空、真实为 0、部分分页、接口失败、时间失效、缺个人记录、缺题面或 ASR 分别验证。 |
| 关键事实 | 对象、时间、人数、状态、分母与证据一致；关键事实不允许因为 Skill 化退化。未知不得冒充真实 0/缺席/完成。 |
| 取数 | 必要证据确实取得，或正确说明不足；区分计划/执行/成功。允许等价正确路径，不强制唯一工具序列。 |
| 教师体验 | 是否答到点、内容是否相关、信息是否够用、是否好读好用；备注进入下一轮评测。 |
| 表达与发送 | 简单事实不强制表格；可比较记录易读；AI 与聊天呈现一致；表格不丢行列、不新增事实。 |
| 一致性与成本 | 关键样本建议各运行 5 次，报告单次通过率、5 次全过情况及失败类别；同时报告 Token、调用次数和 p50/p95 延迟。 |

已有代码回归用于确定性行为；断言 Prompt 中有一句话，不等于模型稳定遵循。采用代码核对数字/对象、人工审阅业务语义，模型评分可辅助但须人工校准。上述重复次数为项目建议，具体样本、门槛和成本预算在实施 Spec 中冻结。

既有关键事实验收标准不因迁移而降低。有限样本全部通过也不能宣传为任意真实问题 100% 正确。没有证据的新增能力和外部接口缺口仍保留条件通过或阻塞。

### 6.3 老师的审阅方式保持简单

老师继续评价问题和回答。可补充信息用业务语言表达，例如“是否希望同时看到迟到与早退的分钟数”；不要把本题必须读取的内容伪装成可选补充。工程层负责 Skill、工具、字段和证据完整性，老师有需要时再展开查看。

每次反馈形成一条可回放案例：原问题、实际证据、原回答、教师意见、所修改的方法版本、再次验证结果。先人工审阅并评测通过，再发布新 Skill；不让 Agent 根据一条评价自动修改长期规则并立即上线。

## 7. 建议讨论通过后的实施顺序

| 阶段 | 范围 | 完成条件 |
| --- | --- | --- |
| S0 · 基线与合同 | 确认问题族、关键证据、对照样本、计划/执行事件和现有限制 | 21+10 映射可查；旧版本可回放；形成审阅后的 PRD、Spec、Tickets。 |
| S1 · 方法集中与小样本试点 | 最小常驻规则、通用/输出规范，试点录播进度 B3、个人学情 D1、课堂回顾 E2；保留既有业务 Adapter | 相同事实下回答不退化；解决重复规则；Skill 加载/版本/失败行为可验证；表格发送前后回归通过。 |
| S2 · 自由问题路由 | 固定入口 ID；自由问题语义路由先只记录与对照，不影响现有取数，再分范围启用 | 上述误路由与复合问题进入回归；对象澄清正确；计划和实际执行可独立核对。 |
| S3 · 全范围迭代 | 扩展到其余问题族、21 题与 10 推荐，纳入反馈回放与版本回退 | 全范围对照与既有回归通过；条件能力保持真实标签；质量/一致性/成本报告可审阅。 |

结构化 AnswerDocument 仅在前面结果证明必要时单独设计，不作为 Skill 化第一阶段的前置条件。
