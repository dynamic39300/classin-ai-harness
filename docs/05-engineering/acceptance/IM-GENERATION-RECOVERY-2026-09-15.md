# IM 生成失败排查与恢复（2026-09-15）

## 范围与证据

针对原版 `classin-ai-harness` 的“生成未能完成，请稍后重试”故障。Write Set：Harness 启动进程生命周期、错误投影及契约、现有失败恢复策略、对应回归测试。本次没有修改 V2、端口、模型凭据、教学建议、数据接口或 IM 发送流程。

从本机失败记录确认两层故障：

1. 用户会话选用 `company-gateway/gemini-2.5-pro`，每次重试返回 `TRANSPORT / Connection error.`。主 Harness HTTP 服务仍监听 3080，但其环境指向的临时 loopback 转接端口连接被拒绝。拥有转接服务的启动进程已经消失，脱离的 npx/Harness 子进程仍在运行，因此主机健康检查通过，模型请求却持续失败。具体是什么外部操作终止启动进程，现有记录无法确定。
2. 恢复转接服务后，用旧会话完整历史隔离重跑，模型返回 `CONTEXT_WINDOW_EXCEEDED`。此前连接失败掩盖了这个长上下文问题。新建文字会话的成功测试无法覆盖旧图片会话的模型路由和历史容量。

原始日志、请求和会话副本只保存在被忽略的 `.runtime/general-question-acceptance/`，未提交学生原文、图片或凭据。

## 修复行为

- `scripts/harness-process.mjs` 在独立进程组中运行 npx/Harness，并通过 IPC 监测拥有模型转接服务的启动进程。IPC 断开即终止本组后代；POSIX 先 TERM，再有界 KILL。避免形成“主机在线、转接服务已死”的孤立进程。正常退出仍传递退出码并关闭转接服务。测试实际覆盖祖父进程被 SIGKILL 后孙进程 HTTP 服务停止。
- 错误投影对 `TRANSPORT` 返回明确的 AI 服务连接失败提示，保留已有输入/消息；不暴露上游错误原文、地址、模型内部信息或凭据。
- `CONTEXT_WINDOW_EXCEEDED` 以显式 `context-window-exceeded` 契约返回。用户下一次明确提交时复用现有恢复路径，创建干净处理上下文并重新采集业务数据；当前逻辑对话保留旧处理记录。不会自动重发、发布消息或切换用户可见 session。
- 这不是无限上下文或无损历史压缩。旧聊天仍可查阅，但旧 AI 历史不会全部输入新一轮模型；用户须明确本次要求，继续分析旧图片时需要重新附图。提示文案直接说明这一限制。普通连接失败不触发清空历史。
- 已仅重启原版 Harness，保留 `.runtime` 会话、草稿和文件；前端继续使用 4173。

## 验证

先复现红灯，再修复：

- 真实失败日志投影复现通用报错；启动测试复现父进程退出后模型主机仍可访问。
- 错误投影/恢复策略测试先失败，再通过；HTTP 类型校验接受新增失败类型。
- `npm run test:harness`：16 项通过，包含签名回放、桥接 HTTP 与进程树退出。
- 目标 Vitest：5 文件、72 项通过（投影、服务端 Runtime、HTTP Adapter、恢复策略和共享 Sidecar）。
- Playwright 4 项通过：一级消息入口、班级聊天入口（均含可访问性扫描）、引用群消息，以及长上下文失败后的下一次提交恢复。恢复后旧、新教师消息均保留，绑定保存原历史引用。
- TypeScript 与本次文件 ESLint 通过。
- 实际服务：在原会话复核并记录上下文超限；将同一完整请求（含业务上下文和所指群聊问题）交给新的处理上下文，最终 `idle`，返回 407 字答复。没有发送正式 IM 消息。
- 真实图片链路：经产品 BFF → Harness → 转接服务 → Gemini 提交固定红色测试图，最终 `idle`，回答“红色”。

限制：进程树故障测试在 macOS/POSIX 上通过；Windows 使用 taskkill，但本次未在 Windows 实测。原始失败日志回放会忠实保留失败状态，不能将历史失败改造成成功；恢复成功以新执行结果验证。
