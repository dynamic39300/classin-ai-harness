# IM 基于学情的个性化师生沟通研究记录

## 1. 研究问题与证据边界

本记录回答五个问题：Notion 方案中的四项 AI 功能分别需要哪些输入、分析和教师干预；班级群与教师—学生 1v1 的交互有什么差异；IM 样本数据说明了什么；当前仓库已经具备哪些承载能力；使用 DW Hunter 接入真实业务上下文时必须遵守哪些数据边界。

本轮读取了 Notion 原页和 DW Hunter 知识库，并检查了当前仓库实现。首次连接时 `dw-conn-mcp` 因 Authorization 失效返回 401；用户刷新令牌后，初始化返回 200，并开放只读权限、元数据与查询工具。本轮随后执行了受分区约束的只读查询，取得教学群行级样本。仓库保存去标识化业务投影作为默认 Fixture；经用户明确授权，另在 Git 忽略的 `.runtime/private` 中保存一个本机精确消息快照，用于真实群名、聊天原文和 DeepSeek 上下文的端到端验证。数据库 UID、群 ID、消息 ID、SQL 与凭据不进入该快照或仓库。

## 2. 数据分析结论应如何理解

Notion 研究以 8 月份 **8,197 个 IM 会话**（包含私聊、群聊）为总体来源，抽取 **1,000 个聊天窗口**，并在每个窗口内按时间顺序抽样 **100 条消息**。这三个数字分别代表来源会话数、分析窗口数和单窗口消息样本上限，不能相互替代。[NOTION-IM-610]

1,000 个聊天窗口由以下渠道组成：[NOTION-IM-610]

| 渠道 | 窗口数 | 在 1,000 个窗口中的占比 |
| --- | ---: | ---: |
| 课程班级群 | 780 | 78.0% |
| └ 师生群 | 741 | 74.1% |
| └ 老师群 | 39 | 3.9% |
| 1v1 私聊 | 220 | 22.0% |

741 个师生群进一步分为 **578 个多学生班级群（78.0%）** 和 **163 个单学生班级群（22.0%）**。这里的 578 与 163 的分母是 741 个师生群，并非全部 1,000 个聊天窗口。单学生班级群仍是课程班级群，拥有班级/课程关系和群治理语义，不能因为只有一名学生就当作普通 1v1 联系人会话。[NOTION-IM-610]

这些结果说明班级群是主要教学沟通现场，同时单学生班级群占师生群的五分之一以上，围绕单个学生的持续服务已有显著使用场景。它们不足以直接证明全部 8,197 个会话中的总体比例，因为原页没有说明窗口抽样的随机化、去重、区域/机构覆盖和置信区间；产品排序可以把它作为场景证据，不能把样本占比当作生产流量预测。[NOTION-IM-610]

### 2.1 本轮真实行级样本

本轮先以 `dt` 裁剪 2026-08-25 至 2026-09-08，核验消息最新可用分区为 2026-09-07，14 天窗口共 7,891,751 条消息。随后只在 2026-09-01 至 2026-09-07 的群消息分区中，以教育语义关键词和最小活跃度筛选 80 个候选群，从中选取一组适合四项功能验证的教学沟通样本。[DW-CONN-IM-20260908]

选中群在 7 天内包含 96 条消息、14 位发送者，出现开课召回、迟到、请假、课后内容回顾和表达/思辨教学等真实模式。以群内共同发送者引用向前查找 30 天联系人会话，得到 19 个候选并选取一条包含 16 条消息的会话；内容包括 Problem–Solution 概念、故事要素定位、情节顺序、阅读理解、词汇复习和独立造句反馈。联系人数据在当前数仓投影中只出现单侧发送记录，因此“未看到学生回执”只能标为待确认，不能推断学生未读或未完成。[DW-CONN-IM-20260908]

消息表的已见 `msgcmd` 对应 JSON 均核验为 `content + strTalker` 结构后才解析。原始 `clusterid`、`sourceuid`、昵称和正文只存在于权限受限的临时文件；Demo 中的“表达与思辨体验班”“林悦”和消息均为不可逆化名及语义改写。群成员视图在 Impala 中遇到日期类型兼容问题，在 Hive/StarRocks 查询时限内也未完成，因此当前“同群参与者 → 联系人会话”的关系只证明共享参与者引用和内容语义，不等于已经完成生产级教师、学生、机构与课程身份校验。[DW-CONN-IM-20260908]

原页列出的高频教学主题也支持四项功能的选择：在多学生/单学生班级群中，课程改期等提醒类沟通分别占 19.2%/41.1%，作业布置完成与订正占 12.1%/29.4%，日常学习表现与反馈占 8.7%/22.7%，课程内容范围与进度占 4.3%/11.7%，到课/请假/缺勤处置占 15.1%/16.0%。原页没有说明主题是否互斥，因此这些占比不应相加为 100%。[NOTION-IM-610]

## 3. 四项 AI 功能：输入、分析与干预

共同闭环是：**业务系统提供可信状态 → AI 解释和生成 → 教师选择对象、审阅并确认 → IM 发送 → 后续行为回流**。AI 生成文本不能直接改变 ClassIn 消息、作业或学生事实。[NOTION-IM-610][PROJECT-DECISIONS]

### 3.1 个性化提醒

| 阶段 | 要求 |
| --- | --- |
| 输入 | 课程安排、改期/补课状态、到课情况、作业提交状态、订正/重做状态、提醒截止时间，以及当前班级或学生的授权关系。[NOTION-IM-610] 作业侧可由作业配置、学生作业详情和作答/批阅日志提供 `status`、`reform`、`readover`、`ref_time` 等证据；这些只是候选字段，正式 Adapter 仍须按实际表和权限核验。[DW-KB-105.8] |
| AI 分析 | 先以规则/查询确定“谁、因为什么、何时需要提醒”，再由模型按原因、时限和对象关系生成适当话术。模型不得自行猜测未提交、缺勤或改期事实。[NOTION-IM-610] |
| 教师干预 | 系统展示筛选依据和待提醒名单；教师增删对象、编辑话术、确认发送范围；发送后显示成功、部分失败或权限问题，并支持查看后续提交/订正状态。[NOTION-IM-610] |

### 3.2 个性化课堂回顾

| 阶段 | 要求 |
| --- | --- |
| 输入 | 明确课次、课程目标、教学内容与进度、课堂参与、学生作答和必要的教师观察；必须知道面向哪名学生生成。[NOTION-IM-610] |
| AI 分析 | 提炼本课重点和完成进度，将班级共性与个人证据分开，识别该学生需要巩固、表扬或继续关注的点，生成面向学生可理解的个人回顾。[NOTION-IM-610] |
| 教师干预 | 教师选择课次和学生，查看引用的课堂证据，审阅“我的课堂回顾”卡并修改；确认后通过 IM 发送，学生可查看或下载。没有个人证据时应请求补充或降级为班级回顾，不能生成伪个性化结论。[NOTION-IM-610] |

### 3.3 错题解析与再练

| 阶段 | 要求 |
| --- | --- |
| 输入 | 原题、标准答案、学生原始作答、批改结果、错题定位和知识点；作业侧还可读取学生留言、作答内容、教师评语、得分、正确/错误数量、提交和重做记录。[NOTION-IM-610][DW-KB-105.8] |
| AI 分析 | 定位第一个关键错误步骤，区分概念、方法、计算或表达问题；生成分步解析，并推荐或生成一道与错误原因直接相关的再练题。标准答案与学生原答必须保持可追溯，不能由模型补写成“系统事实”。[NOTION-IM-610] |
| 教师干预 | 批改后识别错题，教师审阅解析、答案呈现策略和再练题，确认后私密发送给目标学生；学生作答需回流到同一任务，供教师或系统复查。群聊只适合共性问题，不应公开个人作答、成绩或错误画像。[NOTION-IM-610] |

### 3.4 个人学情总结

| 阶段 | 要求 |
| --- | --- |
| 输入 | 指定学生、统计周期、课堂表现、作业/订正、互动、教师反馈和阶段变化。不同来源必须携带各自时间范围和新鲜度，不能把 T-1 快照与当前实时状态混成同一时点。[NOTION-IM-610][DW-KB-010][DW-KB-213] |
| AI 分析 | 按“进展—困难—下一步”归纳，区分可观察事实、教师原始反馈和 AI 推断；比较必须使用同口径周期，避免由单条消息或单次低分给学生贴标签。[NOTION-IM-610] |
| 教师干预 | 教师选择学生与周期，查看证据范围，审阅/删改总结并确认发送；报告发送后继续接收课堂、作业和沟通回流，用于下一次总结。空数据、来源过期或相互冲突时应明确提示，不能静默生成完整报告。[NOTION-IM-610] |

## 4. 群聊与教师—学生 1v1 的交互差异

| 维度 | 班级群 | 教师—学生 1v1 |
| --- | --- | --- |
| 目标对象 | 当前课程群是稳定范围，但可以是多学生群或单学生班级群；提醒类功能还需显式增删学生。单学生班级群继续保留 `class` 渠道，不改成 `direct`。[NOTION-IM-610][DW-KB-213] | 当前 Thread 已锁定一个学生，通常无需再次选择收件人；仍要核验该联系人是学生且与授权班级相关，不能把普通教师/联系人私聊当成学生学情场景。[DW-KB-213] |
| 可见性 | 教师 Sidecar 中的分析和草稿只对教师可见；经教师确认后，内容才以教师身份进入群聊。个人错题、成绩或学情判断不应为了方便而公开到群里。[PROJECT-DECISIONS] | 建议和证据只在教师 Sidecar 可见；当前实现通过“插入回复框”交给教师最后发送，避免 AI 自动向学生发言。[PROJECT-DECISIONS][CODE-SIDECAR] |
| 个性化粒度 | 多学生群优先处理共同事项、分组名单和适合群内公开的话术；个体敏感内容应转为私聊。单学生班级群虽可高度个性化，仍执行课程群的成员与历史语义。[NOTION-IM-610] | 围绕一个学生保留连续上下文，适合课堂回顾、错题解析和个人学情总结；上下文不得混入其他学生或班级 Thread。[PROJECT-DECISIONS] |
| 发送 Gate | 需要清晰展示群名、对象数、最终正文、Context 版本和发送回执；若 Context 已变化，应重新复核。[PROJECT-DECISIONS][CODE-SIDECAR] | 先形成可编辑草稿；插入 Composer 后时间线不变化，仍需教师使用原生发送动作。若未来直接发送，也必须独立审批，不能复用群发 Action。[PROJECT-DECISIONS][CODE-SIDECAR] |
| 回流 | 提醒结果按对象跟踪提交、订正、到课等状态；部分失败不能表现为全成功。[NOTION-IM-610] | 跟踪目标学生的查看、下载、回复或再练提交，同时避免将私聊正文自动暴露到班级群。[NOTION-IM-610] |

Notion 还定义了两种独立的 Agent 渠道：群内显式 `@Agent` 后 Agent 公开回复，以及老师/学生进入 Agent 独立私聊后进行私密多轮对话。[NOTION-IM-610] 它们与本轮“教师私密 TeachBuddy Sidecar”不是同一身份或可见性模型。四项学情服务进入 Sidecar 时应继续执行教师审阅 Gate；不能因为原页展示了群内 `@Agent`，就让教师私密 Sidecar 的 DeepSeek 直接公开发言。[PROJECT-DECISIONS]

## 5. DW 数据接入约束

### 5.1 时效与快照一致性

- 全局指南将原始数据层描述为实时可查，将 Hive/Impala/StarRocks 数仓描述为 T-1，数据应用则按自身刷新周期更新，BI 通常为 T+1 上午。任何 Context Snapshot 都必须逐源记录 `capturedAt`、业务截止时间和 `freshness`，不能只写“最新”。[DW-KB-010]
- IM 消息表是 T-1 日增量，并按 `dt` 分区；群成员和用户群关系是 T-1 全量快照。分析历史消息时必须明确使用“消息发生时身份”还是“当前成员身份”，不能用当前快照反推历史状态。[DW-KB-213]
- 消息业务时间使用 `timetag`，查询仍必须使用 `dt` 裁剪分区。跨作业、课堂和 IM 组合时，应先对齐各源的截止时间；无法对齐时在 UI 和 Prompt 中显式说明。[DW-KB-213]

### 5.2 最小化与脱敏

- 首次真实数据验证只应选择经过授权的一个租户/机构和一个教师范围，在 Adapter 内完成权限校验；仓库中只落固定、脱敏、可重置的演示投影，不提交真实 UID、学生姓名、联系方式、原始消息或凭据。[PROJECT-DECISIONS]
- 手机、邮箱、身份证、银行卡等必须按全局指南脱敏，密码字段禁止查询和输出。IM 群成员表还包含电话、邮箱和个人说明；四项功能通常不需要这些字段，应直接从 SELECT/投影中排除，而不是先读取再交给模型。[DW-KB-010][DW-KB-213]
- 学生姓名在 Demo 中使用不可逆化名；稳定关联只保留 Adapter 内生成的假名引用。消息只读取完成当前任务需要的短时间窗和少量字段，来源正文不得进入 URL、无治理长期记忆或仓库知识缓存。[PROJECT-DECISIONS]
- 个体课堂、作业、成绩和聊天内容属于学生个人数据。群聊生成前必须再检查公开范围；学情总结和错题作答默认私密发送，群聊只使用必要的共同结论。[NOTION-IM-610][DW-KB-105.8]

### 5.3 IM 消息解析限制

- 数仓 IM 文档说明 `msgdata` 在接入数仓时由二进制转换为文本 JSON，同时明确它的类型和解析方式由 `msgcmd` 决定。因此 Adapter 必须先按 `msgcmd` 选择已验证解析器；未知指令、附件或缺少协议的内容标记为不可解析，不能把 `msgdata` 一律当普通文本送给模型。[DW-KB-213]
- 一条消息由 `clusterid + msgbucketid + msgid` 共同定位。`sourceuid` 是发送者，`targetuids` 是接收者列表，二者粒度不同；回复链使用 `replymsgid`，不能当作当前消息 ID。[DW-KB-213]
- `clusterid` 是数仓 IM 视图的统一关联键；课程群与联系人会话不能只凭群成员数区分。课程群、单学生班级群、普通 1v1 必须在 Adapter 映射时保留不同渠道语义。[DW-KB-213][NOTION-IM-610]
- 消息正文属于个人信息。只有解析成功、渠道/参与者通过权限校验且经过字段最小化的消息，才能进入 Context Snapshot；解析失败计数应成为可见数据质量信息，而不是由模型猜测缺失内容。[DW-KB-213]

### 5.4 作业上下文限制

`105.8-原始数据-LMS活动-作业.md` 可以支持作业详情、学生提交/批阅状态和按 `stu_homework_id` 追踪的作答/批阅日志；教师操作日志中的 `uid` 是操作人，不一定是目标学生，按学生取完整过程应使用 `stu_homework_id` 关联。附件字段虽然存在，也不应默认下载或注入模型。[DW-KB-105.8]

仅凭该文档还不能证明原题、知识点、题库关系和可推荐再练题已经拥有完整可用的查询链路。错题解析功能接入真实数据前，必须继续用 DW Hunter 检索相应题库/作答来源，并由 `dw-conn-mcp` 用实际元数据和样本验证；若链路不完整，产品应显示“需要补充题目/知识点”，不能拼凑答案。

## 6. 当前代码能力与缺口

### 6.1 已具备的承载能力

1. IM Sidecar 已与主工作台复用 `AgentRuntimeAdapter` 和真实 DeepSeek Runtime，按消息 Thread 绑定 Session，并支持在 Sidecar 和主工作台恢复同一会话。[CODE-SIDECAR][PROJECT-DECISIONS]
2. `BusinessContextAdapter` 已形成数据来源无关的 Seam，Context Snapshot 带来源、权限、捕获时间、时效、版本、敏感级别和真值标签；类型已预留 `dw-hunter` 与 `classin-api`。[CODE-CONTEXT]

## 7. 下一阶段可验证的真实数据接入顺序

当前 Demo 的正确真值描述是：**真实 DeepSeek + 仓库内去标识 Fixture + 本机授权的真实 IM 只读快照 + 原有固定物理场景 + 模拟 ClassIn 写回**。它证明了真实群名、近期消息和背景证据进入同一 Agent 的纵向切片，但不代表生产实时查询、身份关系或 ClassIn 正式写回已经完成。
