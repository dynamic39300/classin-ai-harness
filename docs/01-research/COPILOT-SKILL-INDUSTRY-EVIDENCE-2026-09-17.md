# Copilot Skill 分层的一手行业证据

本次仅研究和讨论，不修改产品实现、模型配置，不安装 Skill。本文描述的是公开标准和官方实践，不能视为当前 DeepSeek Runtime 已支持相关能力的证明。项目现状和迁移方案由配套讨论稿核查。

## 结论

可以把可复用的问题处理方法、证据解释方法和输出规范组织成 Skills，以便独立维护、按需加载和逐项评价。**Skill 包装本身不保证路由正确、业务事实准确或输出格式稳定。** 稳定性仍须由可执行的业务合同、数据校验、渲染组件和行为评测共同提供。

这里的 Skill 更接近“Agent 按需读取的一份操作指南及配套资源”。加载 Skill 不等于启动一个独立 Agent，也不天然对应一次独立的答案生成调用；如果运行时通过工具读取 Skill，会增加工具交互，实际模型轮次和延迟取决于宿主实现。[Agent Skills 集成指南](https://agentskills.io/client-implementation/adding-skills-support)

## 已核实的文档事实

以下七项均来自一手来源；“对本项目的启示”是本研究的设计判断。

| 证据 | 文档事实 | 对本项目的启示 |
| --- | --- | --- |
| S1 · 开放格式 | Skill 至少包含带 `name`、`description` 的 `SKILL.md`，可附脚本、参考和模板；先加载元数据，选中后加载正文，资源按需读取。`allowed-tools` 为实验字段，支持因客户端而异。[格式规范](https://agentskills.io/specification) | 问题处理经验可以版本化封装；工具授权不能仅靠 Skill 中的一句话。 |
| S2 · 宿主集成 | 官方集成指南列出文件读取、专用激活工具和程序注入。激活时给模型的是说明内容；专用工具可以用合法名称枚举限制可选 Skill，并记录激活事件。[集成指南](https://agentskills.io/client-implementation/adding-skills-support) | 当前 Runtime 需要真正实现发现、加载和记录；把 Prompt 改名为 Skill 不等于已经实现按需加载。 |
| S3 · 工程实践 | Anthropic 把 Skills 定义为可组合的说明、代码和资源；建议从代表任务中的失败出发，先评测再增量构建，并观察描述是否导致合适触发。确定性操作可交给代码。[Agent Skills 工程实践](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills) | 优先迁移已有反复修正的知识；人数、时间和覆盖率计算继续保留代码实现。 |
| S4 · 工作流与 Agent | 官方区分预定义代码路径的 workflow 与模型动态控制的 agent。Routing 将输入分配至专项任务，分类可以由 LLM 或传统算法完成；复杂度应按需求逐步增加。[Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) | 不必为每个 Skill 建立独立模型节点；固定入口和自由问答可采用不同路由机制。 |
| S5 · 可控路由示例 | LangGraph 官方示例让模型生成限定枚举的路由结果，由条件边执行对应节点。模型分类和流程执行分开表达。[Workflows and agents](https://docs.langchain.com/oss/python/langgraph/workflows-agents#routing) | 可借鉴“模型选择、代码执行并验证”的模式；这不是必须引入 LangGraph 的理由，也不证明分类语义必然正确。 |
| S6 · 工具合同 | MCP 工具暴露名称、说明和输入 Schema，可声明输出 Schema。输出结构由服务端提供，与模型受约束生成属于不同机制。[MCP Tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools) | Skill 说明“为什么、何时、如何使用证据”；Tool/Adapter 实现实际 API 调用、入参约束和返回结构，二者不互相替代。 |
| S7 · 评测 | Anthropic 建议结合代码、模型和人工评分；同时测试应触发与不应触发的情形。一次成功不能代表稳定性，应重复试验；结果评估不宜强制唯一工具顺序。[Agent evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) | 教师仍以问答相关性、完整性和好用程度评分；工程层验证事实、必要证据、边界与格式，允许等价的正确取数路径。 |

S4 是 2024 年文章；页面明确提示部分工具生态已变化。本文只借用其工作流、路由和复杂度原则，不据此锁定当前 SDK 或供应商能力。其余动态文档均按本次查阅状态记录。

## 概念边界：哪些应当变成 Skill

下表为设计建议，尚未进入实现规格。

| 环节 | 推荐承担者 | 判断依据 |
| --- | --- | --- |
| 识别老师意图、问题族、所指对象与时间 | 路由指导 + 可验证的路由合同 | 自由语言需要模型解释；合法问题族、对象范围和拒绝越界由代码约束。 |
| 固定推荐入口对应哪个业务任务 | 已知入口的确定性映射 | 老师点击的入口已有稳定任务标识，不必再让模型猜一次。 |
| 某类问题必须核对哪些证据、如何解释缺失 | 问题族 Skill | 这是可复用、需要持续审阅的业务方法。 |
| 未覆盖问题如何澄清、如何基于已有证据回答 | 通用回答 Skill + 常驻的最小事实规则 | 通用 Skill 提供方法；不编造和不跨对象等底线不能依赖可选触发。 |
| 何时用表格、列表、段落，如何组织答案 | 输出表达 Skill | 可积累示例和反例，但需要观察模型是否遵循。 |
| 表头字重、首列强调、溢出控制、发送前后同样呈现 | 共享渲染组件和 UI 测试 | 视觉行为属于程序职责，不能靠模型反复记住样式。 |
| API 地址、字段适配、分页、聚合、时间和身份判断 | Tool/Adapter/Domain 代码 | 可执行的业务事实不应因措辞变化而漂移。 |
| 权限、发送审批、幂等、业务事实新鲜度 | Harness 与领域校验 | Skill 可解释过程，但不能取代强制检查。 |

因此，“每一道问题一个 Skill”不是默认的最佳粒度。更适合先按共享证据和业务语义划分问题族，例如课程与排期、出勤与参与、作业测验、课堂内容、学情摘要、群聊跟进；具体数量须由现有问题和实现盘点决定。一个问题族可包含多个问题模板，一个跨域问题也可能使用多个问题族。这个划分是待验证的项目建议，不是开放标准规定。

## 推荐的初始组合方式

建议先采用一个主 Agent，按需组合少量 Skills：

1. 常驻最小规则：事实来自工具结果、说明覆盖范围、遵守对象隔离和交付边界。
2. 路由指导：自由问题形成业务问题族及对象、时间范围；明确缺少信息时澄清。已知入口直接提供任务身份。
3. 加载对应问题族方法：列出必要证据、可补充证据、禁止的推断和业务术语；支持组合问题。
4. 调用现有工具并由代码核验结果，再依据已取得的证据形成答案。
5. 应用共享表达规范，渲染与发送后展示由同一组件保证。

以上是逻辑环节，**不等于五次串行模型调用**。先尝试在同一 Agent 回合内加载必要说明并调用工具；只有错误分析证明独立判断或修复回合有效时，再增加额外模型调用。此建议依据 S2 的加载机制及 S4 的复杂度权衡，并不承诺一定降低 Token 或延迟。[集成指南](https://agentskills.io/client-implementation/adding-skills-support) [工作流原则](https://www.anthropic.com/engineering/building-effective-agents)

## 如何判断拆分是否值得

以下为本项目拟议的验证设计，具体阈值应在实施规格阶段冻结。

- **比较对象**：现有实现作为基线，同一模型配置、同一问题和固定的真实 API 回放快照对照 Skill 版本。私有样本仍放受限运行目录，不进入公开研究文档。
- **样本来源**：已验收的业务问题、系统推荐入口、用户曾指出的错误，再加入改写、含糊对象、跨问题族、空数据和缺少接口的情况。
- **教师评价**：答到点、事实可信、信息够用、容易读、可直接采用。无需老师检查 Skill 名称或工具全集。
- **工程检查**：选中问题族是否合适、必要证据是否齐备、对象与时间是否正确、是否把未知当缺席/零分、调用是否越界、发送后表格是否保留。
- **反例检查**：简单事实不应强行表格化；只有班级总人数时不能生成个人出勤；用户只问信息时不应擅自生成发送动作。
- **稳定性与成本**：对关键问题重复试验，同时报告单次成功率、重复全部通过的情况、Token、工具次数和延迟；不能只展示最好的一次输出。
- **变更记录**：保存 Skill 名称与版本、触发来源、所选问题族、实际工具结果和校验回执；不收集原始思维链。

这些检查分别评价结果质量与过程约束；不要求模型逐字复制标准答案，也不要求所有正确答案遵循完全一致的工具顺序。S7 支持这种结果与约束分开检查、重复试验和人工校准的方向；上述具体样本与指标为项目建议。[评测实践](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

## 当前不能据此宣布的事项

- 未证明现有 DeepSeek + Harness 已实现标准兼容的 Skill 发现、加载、去重和跨回合保留。
- 未证明模型能稳定识别所有问题族、正确组合多 Skill，或正确处理相互冲突的说明。
- 未证明改成 Skills 会比当前 Prompt 提高准确率、降低成本或减少延迟。
- 未证明任何接口缺口会因 Skill 化而消失；Skill 不产生新的真实业务数据。
- 未授权迁移、安装、配置变更或使用真实账号执行额外业务操作。

后续讨论应先确定问题族、常驻规则与可选知识的边界、Skill 激活方式和评测门槛，再形成 PRD → Feature Spec → Tickets。当前状态保持 `RESEARCH_ONLY`。
