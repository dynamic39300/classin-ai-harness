# ClassIn PC 二阶段体验与视觉品质升级里程碑

**版本**：v0.3
**日期**：2026-08-09
**状态**：`DRAFT / IMPLEMENTATION BLOCKED`
**阶段定位**：第一阶段功能全集完成后的体验重构基线；当前可继续研究，须先完成移动端到 PC 的功能对齐收尾

## 1. 里程碑声明

ClassIn PC Optimizer 第一阶段以功能完整映射、核心业务闭环、双角色架构和高保真可运行 Demo 为主要目标。第二阶段将在不破坏既有业务逻辑、角色权限和功能可达性的前提下，集中提升页面结构、交互体验、视觉品质和产品审美。

第二阶段不是继续增加功能，也不是对现有页面进行表层换肤，而是一次独立的页面级体验重构：从“功能完整、可以使用”继续演进到“结构简明、自然高效、美观优雅”。

本文件是二阶段体验设计工作的项目级里程碑文档。后续讨论产生的共识、方法、试点结论和验收标准持续归档于此；正式实施前，仍需为具体页面或页面原型建立对应 Spec。

## 3. 当前核心问题

### 3.1 页面不够简约、一目了然

全局导航和角色框架基本成立，但进入具体功能后，页面内部存在以下问题：

- 信息虽然完成聚类，却缺少一个统领全页的主结构和主要阅读轴。
- 多个小板块在上下左右同时出现，分栏数量过多，页面呈现出零碎、补丁式的拼接感。
- 不同模块的视觉权重过于接近，用户进入页面后难以迅速判断先看什么、下一步做什么。
- 辅助信息、状态说明和次要功能被过早展开，增加首屏认知负担。
- 功能完整性通过大量可见区块证明，导致页面更像 Feature 清单，而不是自然的工作过程。

### 3.2 页面不够美观、优雅

- 页面构图缺少稳定比例、连续节奏和清楚的视觉重心。
- 组件在局部成立，但缺乏页面级编排，组件化逐渐表现为碎片化。
- 卡片、边框、底色和分栏承担了过多信息组织职责，对排版、对齐、留白和渐进披露依赖不足。
- 多个独立模块同时争夺注意力，视觉层级显得平均，缺少克制和安静感。
- 页面虽然规整，却尚未形成 ClassIn PC 应有的专业性、精致度和独立产品气质。

## 4. 根因判断

当前问题不主要来自颜色、圆角或单个组件质量，而来自页面级体验目标的优先级：

1. **功能完整性优先于任务效率**：设计首先回答了“功能放在哪里”，尚未充分回答“用户最自然的工作路径是什么”。
2. **区块聚类替代了叙事组织**：信息被分组，但分组之间缺少明确的先后关系和上下文连接。
3. **组件边界替代了页面构图**：每个组件都有外观边界，页面缺少更高层的连续结构。
4. **默认暴露过多内容**：缺少渐进披露，次要字段和低频能力与核心任务同时出现。
5. **视觉优化与结构优化混在一起**：容易把拼凑的页面美化一遍，而没有解决信息结构和交互路径问题。

## 5. 二阶段目标

### 5.1 体验目标

- 用户进入页面后 3 秒内理解“这是哪里、当前是什么状态、下一步可以做什么”。
- 每个页面形成一个主要用户任务、一个主要视觉焦点和一条自然阅读路径。
- 核心动作持续可见，辅助内容按需出现，减少无意义的跳转和视线往返。
- 桌面宽幅用于保留必要上下文和提高连续处理效率，而不是填满更多区块。

### 5.2 视觉目标

- 建立专业、克制、现代、精致的 ClassIn 桌面教学工作台气质。
- 主要依靠排版、比例、对齐、留白、层级和节奏组织页面。
- 减少卡片墙、过度分栏、重复标题、装饰性状态块和无必要的视觉边界。
- 让页面具有稳定重心和完整构图，而不是多个漂亮组件的集合。

### 5.3 产品目标

- 保持老师视角与学生视角的业务逻辑、权限和功能完整性。
- 通过信息合并、内容下沉、按需展开和连续操作，提升真实任务效率。
- 将重构成果沉淀为可复用的页面原型和设计规则，而不是逐页做孤立美化。

## 6. 核心设计原则

### P1：一个页面，一个主任务

每个页面必须明确主要用户任务。辅助信息不能与主要任务争夺首屏焦点。

### P2：一个主结构，一条主阅读轴

页面可以有辅助区域，但必须存在清楚的阅读起点、推进方向和结束位置。不能依靠用户自行拼接多个板块之间的关系。

### P3：先做结构减法，再做视觉精修

先决定删除、合并、下沉、折叠和按需展示什么，再讨论颜色、字体、阴影和细节动效。

### P4：页面区块不自动卡片化

Section 优先通过排版、间距、背景关系和细分隔组织。卡片只用于真正独立、可重复或需要对象边界的内容。

### P5：桌面宽幅不等于持续增加分栏

除消息等天然多列场景外，大多数页面默认不超过两个持续可见分栏。第三层信息优先使用按需详情、局部展开或明确转场。

### P6：渐进披露优于全集平铺

首屏展示判断和行动所需信息；详细字段、次要能力和低频操作在用户表达意图后出现。

### P7：组件服从页面构图

设计系统保证一致性，但组件不能独立决定页面结构。页面应先形成完整构图，再选择合适组件承载内容。

### P8：美观必须服务理解和效率

审美升级不能依赖装饰堆叠，也不能以牺牲可读性、可达性和任务效率为代价。

## 7. 目标页面原型

二阶段不为每个页面重新发明结构，而是优先沉淀少量稳定原型：

| 页面原型 | 适用场景 | 主要结构 |
|---|---|---|
| 列表工作台 | 任务、班级、资源 | 稳定列表 + 按需详情 |
| 时间工作台 | 课程表 | 时间主轴 + 当前上下文 |
| 沟通工作台 | 消息 | 分类、会话、内容的必要多栏 |
| 连续分析页 | 教学洞察、学生成长 | 结论 -> 证据 -> 对象/行动的纵向叙事 |
| 沉浸工具页 | 黑板、投屏 | 单一任务舞台 + 克制控制层 |

原型是页面级信息与交互结构，不是视觉模板。不同角色可以共享结构原则，但不能通过大量角色条件拼装同一个页面。

## 8. 案例参照与设计校准

### 8.1 为什么必须引入案例

现有里程碑提供了问题诊断、设计流程和验收框架，但仅依赖 AI 根据抽象原则生成方案，仍存在明显风险：

- “简约、专业、优雅”等目标缺少可观察的尺度，生成结果容易随 Prompt 波动。
- AI 可以减少卡片和分栏，却不一定能够形成稳定、成熟的页面构图。
- 静态页面分析难以覆盖 Hover、选择、展开、详情进入、状态延续和异常恢复等动态体验。
- AI 容易复用常见 SaaS 模板，将一种拼凑方式替换成另一种模板化结构。

因此，二阶段必须建立真实可查阅、尽可能可交互的案例基线。AI 负责研究、拆解、提出假设、生成方案和辅助验证，但不能作为唯一审美事实源。

### 8.2 三角参照体系

不选择单一软件作为 ClassIn PC 的完整模板，而是从三个维度交叉校准：

| 参照层 | 回答的问题 | 候选来源 |
|---|---|---|
| 业务参照 | ClassIn 应该呈现什么业务语义和角色边界 | ClassIn 移动端、当前 PC、真实教学任务、Google Classroom、Canvas LMS、Apple Schoolwork |
| 桌面交互参照 | PC 工作台怎样组织任务、上下文和详情 | Linear、Things 3、Todoist、Slack、Notion Calendar、Fantastical、Figma、FigJam、Airtable、Shopify Admin |
| 视觉气质参照 | 页面如何形成专业、克制、精致的视觉秩序 | Apple、Stripe、Linear 等成熟桌面/Web 产品的排版、比例、留白、边界、色彩和状态细节 |

候选产品只用于启动研究，不代表预先确认其方案适合 ClassIn。每项借鉴必须回到具体用户任务和 ClassIn 业务约束验证。

### 8.3 案例证据要求

案例优先使用真实可操作产品或完整交互记录，不以单张展示图替代体验证据：

- 实际可操作的 Web 或桌面产品。
- 同一任务从入口到结果的连续截图或录屏。
- 默认、Hover、Focus、选中、展开、加载、空、错误和恢复状态。
- MacBook `1440x900` 真实桌面视口表现；其他视口仅作历史参考。
- 完成任务所需的点击、视线往返、上下文切换和返回路径。

Mobbin、Page Flows、Screenlane、Refero 等资料可用于发现案例；Dribbble、Behance 等视觉社区只作为灵感来源，不能单独证明交互正确性。

### 8.4 案例拆解模板

每个纳入案例库的样本至少记录：

| 字段 | 记录要求 |
|---|---|
| 用户任务 | 用户进入页面要完成什么 |
| 主结构 | 单轴、主辅分栏、列表详情或必要多栏 |
| 第一焦点 | 首屏最先被感知的内容 |
| 阅读顺序 | 信息如何自然推进 |
| 默认披露 | 无需操作即可看到的内容 |
| 渐进披露 | 用户表达意图后才出现的内容 |
| 操作路径 | 完成任务的步骤与状态变化 |
| 视觉方法 | 排版、比例、留白、边界、色彩和动效 |
| 可迁移点 | 能解决 ClassIn 哪个具体问题 |
| 不可迁移点 | 与教学业务、角色或品牌冲突的部分 |
| 证据 | 产品版本、访问日期、截图、录屏或链接 |

案例研究必须提取设计决策及其适用条件，不能停留在“像某某产品”的形容。

### 8.5 案例库建议规模

- 选择 `8-12` 个高质量产品建立广度参照。
- 深入拆解 `3-5` 个核心产品任务，而不是只收集首页。
- 提取 `15-20` 个与 ClassIn 页面原型直接相关的交互模式。
- 同时记录优秀案例和典型反例，说明后者为什么造成噪声、割裂或效率损失。

案例库需要足够支撑判断，但不追求无限收集。新增案例必须能够补充新的结构、交互或视觉证据。

### 8.6 ClassIn 内部 Golden Samples

外部案例只能提供校准，最终必须转化为 ClassIn 自己的可交互样本：

- `Golden Screens`：使用真实 ClassIn 内容、经过评审的关键页面和关键状态。
- `Golden Flows`：从入口、操作、状态变化到结果/返回的完整任务流。
- `Golden Patterns`：列表详情、连续分析、时间工作台、沉浸工具等可复用页面规则。

首批内部样本仍选择教学洞察、学生成长和任务中心。每个试点使用相同业务数据构建当前基线与至少两个结构方案，确保比较的是结构和体验，而不是不同内容带来的错觉。

## 9. 二阶段设计流程

### 阶段 0：案例研究与审美校准

- 建立三角参照案例库和案例拆解卡。
- 对三个首批试点分别选择业务、桌面交互和视觉气质参照。
- 收集真实交互流、关键状态和多视口证据。
- 明确每个案例的可迁移点、不可迁移点和适用条件。
- 在结构设计前形成案例研究结论，不直接照抄页面外观。

### 阶段 A：现状结构审计

基于统一视口截图和真实交互完成审计，暂不写代码、不讨论表层视觉：

- 识别页面首要任务和当前实际阅读路径。
- 标记视觉权重过高、重复或缺少上下文的模块。
- 找出不必要的分栏、卡片、标题、工具条和状态说明。
- 明确可以删除、合并、下沉、折叠或按需显示的内容。
- 记录首屏认知负担、操作往返和焦点漂移问题。

### 阶段 B：多方向结构设计

对同一试点页面至少探索两个真正不同的结构方向，例如：

- 单一纵向叙事。
- 主内容 + 辅助侧栏。
- 列表 + 按需详情。

每个方向必须说明第一视觉焦点、主要操作路径、信息披露顺序、桌面空间使用方式，以及相比现状减少了什么。

### 阶段 C：低保真交互原型

- 先验证阅读顺序、任务路径、默认状态和详情展开方式。
- 验证 MacBook `1440x900`；`1280x720` 与 `1024x640` 不作为本轮视觉门禁。
- 用真实业务文本和确定性 Mock 验证布局，不使用无意义 Lorem Ipsum。
- 完成方案对比和评审后才确定高保真方向。

### 阶段 D：视觉语言精修

结构确认后统一处理：

- 字体层级与行长。
- 信息密度与留白节奏。
- 色彩占比和状态语义。
- 边界、控件高度、图标尺度。
- Hover、Focus、选中、展开、加载、空和错误状态。
- 页面之间的视觉一致性与角色叙事差异。

### 阶段 E：实施与验证

- 为试点页面建立正式 Spec，明确保留、删除、下沉和转场规则。
- 逐类页面实施，避免同时铺开全部页面。
- 通过前后截图、任务路径、无障碍和多视口测试验收。
- 将成熟结论更新至 `PC-DESIGN-SYSTEM.md` 和页面原型规范。

## 10. 首批建议试点

### 10.1 教学洞察

验证“连续分析叙事”：从班级判断进入课堂证据，再进入学生行动，重点解决指标块、数据分区和详情之间的碎片化。

### 10.2 学生成长

验证“舒适阅读型分析页”：将诊断、成长指标、课程进度、奖励和学习记录组织为自然证据链，避免学生页面形成 Dashboard 卡片墙。

### 10.3 任务中心

验证“高频列表工作台”：减少工具栏、筛选、列表、状态和详情之间的竞争，在紧凑信息密度下保持清楚、稳定和高效。

三个试点分别代表教师分析、学生阅读和高频操作。试点结论稳定后，再迁移至首页、班级、空间和其他页面。

## 11. 与 AI 的协作协议

二阶段与 AI 的交流重点从“补齐功能”和“优化 UI”切换为“结构审计、设计取舍和体验验证”。

### 11.1 推荐讨论顺序

1. 提供当前页面截图、业务目标、主要角色和第一阶段 Spec。
2. 提供经过拆解的相关案例、交互流和明确的可迁移/不可迁移边界。
3. 要求 AI 复述页面首要任务和当前阅读路径，先验证问题理解。
4. 要求 AI 明确指出应该删除、合并、下沉和折叠的内容。
5. 要求 AI 给出多个结构差异明显的方案，并说明使用了哪些案例原则，而不是只换颜色和排版细节。
6. 先评审结构和交互，再进入高保真与代码实施。
7. 实施后使用同视口截图、Golden Flow 和真实任务逐项对照，不凭抽象描述验收。

### 11.2 标准开场提示词

```text
本轮不是增加功能，也不是对现有页面进行表层美化，而是进行页面级体验重构。

当前全局导航和功能架构保持不变。重点解决：
1. 页面板块过多、视觉权重平均；
2. 分栏过多，阅读顺序不清晰；
3. 卡片化和组件化造成拼凑感；
4. 信息虽然完整，但缺少自然、连续的任务路径；
5. 视觉品味不够克制、简约和优雅。

请先不要写代码，也不要先讨论配色。

第一阶段请基于页面截图完成结构审计：
```

## 13. 验收框架

二阶段不能只以“看起来更好”验收，至少从以下维度评价：

| 维度 | 核心问题 |
|---|---|
| 任务清晰度 | 用户是否能在 3 秒内理解当前状态和下一步操作？ |
| 阅读秩序 | 页面是否存在明确起点、主轴和自然结束位置？ |
| 结构简约度 | 是否减少了无必要板块、卡片、分栏和重复说明？ |
| 渐进披露 | 辅助信息是否在需要时出现，而非默认平铺？ |
| 操作效率 | 核心任务的点击、视线往返和上下文切换是否减少？ |
| 视觉品质 | 构图、比例、排版、留白、色彩和细节是否统一克制？ |
| 桌面适配 | 宽幅是否增加有效上下文，而不是增加视觉噪声？ |
| 一致性 | 页面是否遵循稳定原型，同时保留业务场景差异？ |
| 可访问性 | 键盘、Focus、对比度、语义和状态反馈是否完整？ |
| 案例可追溯性 | 关键设计取舍是否有真实案例或内部验证依据？ |
| 迁移合理性 | 是否说明借鉴内容为什么适合 ClassIn，以及拒绝了什么？ |
| 交互完整性 | 是否验证连续任务和关键状态，而非只比较静态截图？ |

正式实施前为每个试点建立可测量基线，包括首屏板块数量、持续可见分栏数量、核心任务步骤、默认暴露操作数量和 `1440x900` 截图。每个选定方案还必须至少引用一项业务参照和一项桌面交互/视觉参照，并说明其迁移边界。

## 14. 明确不做

- 不在二阶段重新定义已经锁定的角色架构和核心业务规则。
- 不以删除功能换取视觉简洁；低频功能可以下沉，但必须保持可达。
- 不把所有页面统一成同一种 Dashboard 或卡片模板。
- 不只替换配色、圆角、阴影和字体后宣称完成体验升级。
- 不追求脱离教学业务的视觉炫技、营销化 Hero 或装饰性动效。
- 不在没有截图对照、真实任务和多视口验证时接受抽象审美结论。
- 不选择单一产品作为 ClassIn PC 的完整模板或进行像素级照抄。
- 不把静态灵感图、设计社区热度或 AI 生成图单独当作交互正确性的证据。
- 不为扩充案例数量而收集与试点问题无关的页面。
