# WorkBuddy M4.1 对话式 Agent Run PRD

## 1. 产品目的

让教师在一个持续存在的任务对话窗口内理解、控制并完成 Agent Run。页面必须同时回答：Agent 理解了什么、还缺什么、计划是什么、现在做到哪一步、调用了什么能力、产生了什么结果、将改变什么业务对象、实际执行是否成功。

## 2. 目标用户与任务

本阶段聚焦教师的两类任务：

1. 生成单个课件；
2. 生成课程方案包，包括课件、作业、测验和录播脚本。

两类任务使用同一对话壳层和事件语言，但拥有独立 Run、ContextSnapshot、Artifact 和 Receipt。

## 3. 页面结构

```text
┌ ClassIn / Agent 导航 ┬──────────────── Agent Run Surface ────────────────┐
│                       │ Run Header                         [上下文][产出] │
│                       ├───────────────────────┬───────────────────────────┤
│                       │ Conversation Timeline │ Active Inspector          │
│                       │                       │ default: Context          │
│                       │                       │ alternate: Output         │
│                       ├───────────────────────┴───────────────────────────┤
│                       │ Composer + Context Chips + Attachment             │
└───────────────────────┴───────────────────────────────────────────────────┘
```

### 3.1 Run Header

必须显示：

- Run 标题；
- 当前教师可理解的状态；
- Task Type；
- 来源入口或来源 Artifact；
- `上下文` 与 `产出` 入口及数量/状态；
- 收起右侧区；
- 更多操作。

Header 不显示内部阶段编号、Mock 场景选择器、工程 ID、模型隐藏思考或底层状态枚举。

### 3.2 Conversation Timeline

Timeline 是 Run 的唯一主轴，按发生顺序呈现：

- 教师消息；
- Agent 目标理解；
- 结构化补参；
- Context 确认摘要；
- Plan；
- 步骤与能力调用；
- 中间结果；
- Artifact；
- ProposedAction；
- Approval 结果；
- ExecutionReceipt；
- EvaluationEvent（仅表达对象采纳/未采纳与执行状态，不推断教学效果）；
- 错误与恢复。

同一事件只在一处拥有主表达。右侧预览、弹窗和技术 Disclosure 是事件的辅助视图，不复制另一条相互矛盾的状态。

### 3.3 Composer

Composer 固定在 Run 底部，包含：

新任务、当前 Run 补充、历史 Run 追问与 IM 内 WorkBuddy 输入统一遵循 `docs/03-design/WORKSPACE-COMPOSER-STANDARD.md`。页面只投影业务状态与允许命令，不自行维护另一套 textarea、工具栏或发送按钮样式。

- 多行目标/追问输入；
- 附件/资源入口；
- Core Context 入口；
- 已选 Context Chips；
- 发送/停止/继续中的唯一主行动；
- 运行中允许的命令提示。

Composer 根据状态改变能力，不替换为另一张页面：

| Run 状态 | Composer 主要行为 |
| --- | --- |
| 草稿 | 输入 Goal、选择 Context、发送 |
| 等待补参 | 结构化卡为主；Composer 可补充解释 |
| 等待计划确认 | 可输入修改要求或确认计划 |
| 执行中 | 追加约束、停止；普通发送不会自动重启任务 |
| 等待 Artifact 复查 | 输入修改意见、打开产出、确认采用 |
| 等待审批 | 可解释或修改目标；正式审批使用动作卡/弹窗 |
| 完成 | 追问、创建关联任务、重新打开产出 |
| 失败可恢复 | 补充要求、重试或换策略 |

## 4. 标准 Run 生命周期

### 4.1 草稿与提交

1. 教师在新任务 Composer 输入 Goal；
2. 教师可以先在右侧 Context 树选择班级、课程、单元和资料；
3. 每次选择立即形成 Context Chip，但尚未生成 Snapshot；
4. 点击发送后立即创建稳定 Run ID 和历史条目；
5. 用户 Goal 作为第一条不可变消息进入 Timeline；
6. 页面不跳往新的阶段 Route，只在同一 Run URL 中进入动态执行。

提交防重复：发送后主按钮进入处理中；重复点击、回车或网络重试只创建一个 Run 和一条 Goal 事件。

### 4.2 Agent 目标理解

Agent 第一条消息必须使用教师语言说明：

- 我理解您要完成什么；
- 目标班级/课程/主题；
- 预期产物；
- 已使用的 Context；
- 仍缺哪些关键约束；
- 下一步将先补参还是直接给 Plan。

不显示“思考中”的隐藏推理文本。动态状态可使用“正在整理任务要求”，完成后替换为可检查的摘要。

### 4.3 结构化补参

当必需信息缺失时：

1. Agent 先用一句话解释为什么需要补充；
2. 紧接一张内嵌补参卡；
3. 卡片只收集当前步骤必须的信息；
4. 已知 Context 不重复询问；
5. 提交后卡片冻结为“教师已确认”的折叠摘要；
6. Agent 在同一位置继续输出下一条事件。

补参字段可包含：单选、多选、业务对象、短文本、课时、日期、文件和“其他”。必填与可选必须明确；跳过只适用于可选字段。

### 4.4 Core Context 确认

补参完成后，Timeline 产生 Context 摘要卡：

- 班级、课程、单元/主题；
- 选择的计划文档、活动和资源；
- 学习者范围摘要；
- 未带入的敏感信息数量；
- “查看/调整上下文”入口。

右侧默认保持 Context 展开。教师点击“确认并生成计划”后，CoreContext Module 校验层级、权限和必需项并冻结 Snapshot。失败仍停留在同一 Run，右侧树定位到问题节点。

### 4.5 Plan

Agent 提交一张 Plan 卡，而不是跳转到计划页面。Plan 必须显示：

- 对任务的最终理解；
- 计划步骤；
- 每一步的预期输出；
- 将调用的 Skill/Tool 的教师可理解名称；
- 最终 Artifact；
- 需要教师参与的节点；
- 对课程方案包显示依赖关系。

教师可以：

- 确认并开始；
- 提出修改；
- 返回调整 Context；
- 取消任务。

修改 Plan 不创建新 Run；确认后的重大目标变化触发 Replanning，并保留旧 Plan 为 superseded 证据。

### 4.6 Process

确认 Plan 后，Plan 卡转换为可持续更新的进度卡，Timeline 按顺序追加步骤事件。

每一步包含：

- 步骤标题和教师摘要；
- `等待 / 执行中 / 需要确认 / 完成 / 失败 / 已跳过`；
- 使用的 Skill/Tool；
- 输入 Context 摘要；
- 输出或阶段结果；
- 耗时；
- 可用命令。

能力调用默认只显示“正在调用课件结构设计能力”等教师语言。展开“详细信息”后才显示参数摘要、Context Projection、结果摘要和错误；原始命令、路径、环境变量、Secret 和大段 JSON 不进入默认路径。

### 4.7 动态节奏

确定性 Experience Adapter 必须模拟真实异步行为，但不能用纯装饰动画冒充完成：

| 事件 | 目标节奏 |
| --- | --- |
| Goal 提交 → Agent 开始响应 | 150–500ms |
| “正在整理任务与上下文”状态 | 固定体验环境持续 `2s`，显示旋转加载状态与预计剩余秒数 |
| 补参提交 → Context/Plan | 300–800ms |
| 每个执行步骤 | 固定体验环境每步持续 `3s`；至少经历一次可见 `running`，再进入结果状态 |
| Tool/Skill 调用 | 卡片先出现调用中，显示本步预计剩余秒数，再填入结果摘要 |
| Artifact 生成 | 先产生阶段结果，再产生 Artifact 引用 |
| Action 执行 | Approval 完成后持续 `2s` 显示执行中与预计剩余秒数，Receipt 到达后才显示完成 |

Header 同时显示当前步骤序号与整体预计剩余时间；活动调用卡显示当前步骤预计剩余时间。单课件四步完整生成约 `12s`，课程方案包三阶段完整生成约 `9s`。这些数字是当前固定体验 Adapter 的可解释预计值，不代表生产 Agent 的承诺时长或服务 SLA。

执行中与已暂停状态还必须在 Composer 正上方提供一个紧凑的任务进度胶囊，默认只显示“第 N/M 步”（暂停时同时显示“已暂停”），使教师无需回到 Header 或时间线顶部即可确认当前位置。鼠标悬停、键盘聚焦或点击胶囊时，在其上方展开步骤清单：已完成项显示完成图标和“已完成”，当前项显示旋转加载和“进行中”，未开始项显示中性圆点和“等待”；暂停时当前项改为“已暂停”。清单与胶囊必须直接投影同一份 `progress + plan`，不得建立独立进度状态或推测真实完成度。

进度胶囊上方保留一条低权重的当前执行语句，例如“正在执行 · 理解教学目标”。只有真实 `running` 状态允许文字亮面从左至右扫过，用于表达系统仍在工作；扫光不得应用到整张卡片、已完成内容或暂停状态。步骤推进时语句原位切换到新的当前步骤；暂停时改为静态“已暂停 · 当前步骤”，完成、取消或尚未开始时隐藏。Reduced Motion 下保留静态执行语句并关闭扫光。

进度清单不是仅 Hover 可用的 Tooltip：胶囊必须可聚焦、支持点击切换和 `Escape` 收起，浮层与触发器共同构成连续的悬停区域。Run 完成、取消或尚未开始执行时不保留胶囊，避免与最终状态或计划确认竞争注意力。

自动化测试通过可控 Clock 或 Adapter 驱动，不依赖真实墙钟等待。暂停时冻结当前步骤剩余时间，继续时从冻结位置恢复；刷新恢复不能让同一步骤重新计满或重复执行。教师可以开启 Reduced Motion；事件顺序不因动效关闭而改变，旋转动画关闭后仍保留明确的“正在准备 / 执行中 / 正在执行”文字和剩余时间。

### 4.8 Artifact

Artifact 到达时同时发生：

1. 当前步骤进入完成；
2. Timeline 追加 Artifact 卡；
3. Header `产出` 出现数量和未读状态；
4. 右侧产出区根据自动切换规则展示预览；
5. Timeline 保留 Artifact 稳定引用，关闭右侧区后仍可重新打开。

Artifact 卡显示标题、类型、版本、验证摘要、来源步骤和状态。文档类 Artifact 在右侧区提供当前页紧凑预览，在 Focus Surface 提供全局只读预览：页面目录、上一页/下一页、目录跳转和键盘翻页都不得替换原 Timeline。当前体验环境使用确定性模拟页面，并以 `[模拟]` 明确标注，不暗示已经具备真实 Office 渲染能力。

预览器只负责查看、下载和发起受治理的 ClassIn 保存动作，不承载内容编辑器或 AI 改写输入。教师需要修改 Word、PPT 等专业文档时，通过“使用专业编辑器打开”进入第三方工具；连接尚未实现时必须给出未接入提示，不能伪造打开成功。预览失败时保留文件信息、下载与外部打开入口，并允许教师返回 Timeline 继续任务。

### 4.9 ProposedAction 与 Approval

教师选择“保存到 ClassIn”时，Timeline 先产生 ProposedAction 卡，列出：

- 将执行的动作；
- 目标对象；
- 差异和影响；
- 来源 Artifact 版本；
- 权限、风险和可逆性；
- 过期时间。

低风险、单对象动作可以在卡片中确认；高风险、多对象或部分执行动作打开确认窗口。确认窗口不是新页面，关闭后焦点回到原 Action 卡。

批准只生成 Approval，不显示“保存成功”。执行开始后卡片显示执行中；只有 Receipt 到达才显示最终结果。

### 4.10 ExecutionReceipt

Receipt 作为该 Run 的最终业务结果事件进入 Timeline：

- 成功：实际对象、版本、时间、返回入口；
- 权限拒绝：未执行范围、原因、可选择的新目标；
- 版本冲突：提交版本、当前版本、比较和重新确认；
- 可恢复失败/超时：安全重试，保持 Action/Approval/幂等链；
- 部分成功：逐对象结果和失败项恢复。

Receipt 卡与右侧 Artifact 不互相替换。教师关闭或恢复 Run 后，Receipt 仍在原时间线位置。

## 5. 单课件特有规则

- 只生成一个主 Artifact，不显示空方案包目录；
- 课件完成后先进入教师复查，不自动写回 ClassIn；
- 预览器浏览页码不产生新版本；真实内容修改与版本差异由第三方专业编辑器及未来 Adapter 返回；
- 确认课件可用与批准保存是两个决定；
- 完成后可创建关联方案包 Run，但不改变原课件 Run 状态。

## 6. 课程方案包特有规则

- Plan 显示课件、作业、测验、录播脚本的依赖；
- 过程允许并行步骤，但 Timeline 使用组事件避免无序刷屏；
- 右侧产出区提供方案包目录和选中 Artifact 预览；
- 每个 Artifact 独立版本、状态、审阅结论和恢复命令；
- 批量 ProposedAction 可展开为对象级候选；
- 部分成功不能把整个 Run 显示为完成；
- 重试只执行失败且仍符合条件的对象，成功项不重复执行。

## 7. 运行中教师介入

### 7.1 追加要求

- Composer 在执行中显示“补充要求”；
- 追加内容形成教师消息并关联当前步骤；
- 不影响已完成步骤时，Agent 解释应用范围后继续；
- 改变目标、主班级、主课程或产物类型时，进入 Replanning。

### 7.2 停止

- 点击停止后，正在运行事件先进入 `stopping`；
- Adapter 确认停止后进入 `stopped`；
- 已产生 Artifact 保留；
- 未执行 ProposedAction 不进入执行；
- 可选择继续、从此处新建任务或删除草稿。

### 7.3 修改 Context

- 右侧 Context 树始终可查看；
- 修改次要资料只影响未开始步骤；
- 修改主范围先显示影响分析；
- 教师确认后创建新 Snapshot 和 Plan；
- 旧事件、Artifact、Action 和 Receipt 作为 superseded 证据保留。

## 8. 滚动、自动跟随与恢复

- 教师位于时间线底部时，新事件自动跟随；
- 教师向上滚动后停止自动跟随，并显示“回到最新 · N 条更新”；
- 补参、Plan 或 Approval 需要行动时，即使教师不在底部，也显示固定待处理提示；
- 打开历史 Run 恢复时间线锚点、未发送 Composer、展开的调用卡、右侧模式和选中 Artifact；
- 页面刷新通过稳定 Run ID 恢复 Projection，不依赖 Route 中的阶段参数；
- 不把自动滚动抢焦点当成“实时感”。

## 9. 键盘与焦点

- 新事件到达只通过状态区播报，不自动夺取焦点；
- 提交补参后焦点回到冻结后的补参摘要；
- 打开右侧区，焦点进入 Panel Header；关闭后回到触发按钮；
- 打开 Approval 窗口，焦点进入标题，关闭后回到 Action 卡；
- Artifact Focus 返回后恢复时间线和右侧选择；
- 所有状态同时使用图标和文字，不只依赖颜色。

## 10. 空、加载、异常与恢复

| 状态 | 表达 |
| --- | --- |
| 新任务空白 | Composer + 默认展开 Context；不显示假时间线 |
| 正在创建 Run | Goal 已冻结，Agent 状态显示正在理解 |
| Event Stream 暂停 | 保留最后事件，显示重新连接；不伪造失败 |
| Agent 事件失败 | 对应步骤失败，显示重试/换策略/补充信息 |
| Artifact 预览失败 | Artifact 仍存在，可下载、外部打开或重试预览 |
| 需要教师确认 | 时间线卡 + 固定待处理提示 |
| Action 过期 | 原卡保留，重新生成提案而非静默续期 |
| 历史权限变化 | 敏感正文隐藏，事件骨架和失效原因保留 |

## 11. 页面级验收

- 从发送 Goal 到 Receipt 不发生阶段 Route 跳转；
- Timeline 可观察到理解、补参、Context、Plan、至少三类 Process 事件、Artifact、Action、Approval 和 Receipt；
- 每一步先进入可见执行态，不能一键直接跳到最终完成；
- Skill/Tool 调用卡能展开输入/输出摘要，但默认不暴露内部命令和 Secret；
- 右侧 Context/产出切换不丢 Timeline、Composer、选择和滚动位置；
- 单课件与课程方案包复用同一交互语言；
- Context 修改和追加要求在原 Run 内产生明确 Replanning；
- 真实 Runtime 接入前，页面不会把模拟事件误写为生产推理或真实 ClassIn 执行。
