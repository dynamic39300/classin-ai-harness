# TeachBuddy IM Copilot 情境引导体验提案

## 1. 本轮目标与事实边界

用户已确认：本 Session 细化 Part 1 的前端交互体验，先做整体入口与个性化提醒闭环，后续复用到课堂回顾、错题解析与再练、个人学情总结；公开群 Agent 与师生 Agent 私聊另行设计。

用户提供两类现有入口截图：班级内打开的聊天窗口，以及首页消息聚合入口。两者使用同一套 Copilot 操作；入口位置差异不能创造两份任务或不同的权限规则。截图仅作为既有 UI 与操作背景，不作为生产接口、权限或实现已完成的证据。

用户已审阅本文，并明确确认主卡突出、其他能力紧凑收纳、工作过程中让位于任务和产物的方向。2026-09-09 补充：其他能力可提示可处理事项数量并展开操作；先采集真实业务底稿再模拟时间；上下文默认自动加载，不展示“依据”或要求老师管理上下文。随后进一步确认主卡/副卡的生成按钮应合并意图准备与发送给 AI，一次点击直接发起任务，自由提问进入同一能力。本文已按补充修订。具体角标颜色、计数口径、布局尺寸与提醒阈值仍是细化建议，尚未作为已实现 Feature Spec。

首轮 Write Set：本文与 [一手案例研究](../../../01-research/IM-COPILOT-CONTEXTUAL-GUIDANCE-RESEARCH.md)。本次修订 Write Set：本文、[DW 派生场景数据方案](./COPILOT-DW-SCENARIO-DATA-PLAN.md) 与决策账本中的新增确认记录。不修改应用代码、Part 2 IM 工作或 Notion 原文。IM 卡片的预填后手动提交规则由本次明确确认替代；其他入口保持原范围。

## 2. 核心设计判断

首屏依次回答四个问题：

1. 这是谁的助手？——TeachBuddy，教师私有协作。
2. 正在帮我看哪里？——当前班级/学生与所选教学事项。
3. 现在有什么值得做？——一张有依据、能行动的教学事项卡。
4. 我做到哪里了？——当前任务优先恢复，其他聊天的任务可以找回。

采用“当前主事项 + 带数量的紧凑能力入口 + 自由输入”的分层。主卡负责此刻最值得处理的事项，次要入口负责发现其他可处理工作，自由输入承接老师自己的目标。打开次要入口后以副卡列出具体事项和动作；进入任务后全部能力收纳在输入区旁的“教学协作”，继续保留数量提示。

## 3. 两个入口与首次发现

### 3.1 固定入口

- 两类聊天均在聊天标题右侧保留带文字的 `TeachBuddy` 按钮，配已有品牌图标，紧邻聊天操作但与更多菜单区分。
- 面板展开时按钮显示选中状态；关闭后按钮仍在原位。未完成任务以 `生成中`、`待确认` 等文字状态辅助图标表达，不借用人类未读消息的红色计数。
- 首页消息聚合页必须先选中具体会话才装配其上下文。尚未选择时显示“选择一个聊天，查看相关教学协作”，不聚合读取全部聊天。
- 班级聊天窗口打开右侧面板时优先利用可用窗口宽度。宽度不足则用可返回聊天的单面板模式；不在旧浮窗之外再叠加一个漂浮 AI 窗口。最终尺寸随桌面视觉验收确定。

### 3.2 第一次进入

推荐桌面宽屏首次进入已选聊天时展开一次 Sidecar；此后的展开/收起遵循教师偏好。窄窗口首次只用一条可关闭、锚定入口的提示，避免挤压原聊天。首次状态按教师去重，两种入口不重复新手教育。

面板首次说明只用两句：

> 我可以结合这里的课程、课堂和作业，帮你准备提醒与学习反馈。
> 这里的协作仅你可见，发给学生前由你确认。

说明下直接展示真实可用事项；不要求完成导览、选择模型或阅读六项功能介绍。没有业务证据时允许从课次/作业选择开始，示例意图不能冒充实际待办。

### 3.3 回访与不同状态

| 状态 | 默认主体 | 新建议的处理 |
| --- | --- | --- |
| 首次且无任务 | 简短介绍 + 当前主建议 + 常用能力 | 最多一张主卡，其他收在“还有 N 项” |
| 已使用但无未完成工作 | 当前主建议 + 常用能力 | 不再重复长欢迎语 |
| 有未提交要求或已选对象 | 恢复输入和选择 | 小型“新的教学事项”入口，不覆盖草稿 |
| 生成中 | 原任务与真实过程反馈 | 保持原位置，不重排、不抢焦点 |
| 待确认 | 原产物、对象、发送目的地 | 新事项折叠，不把成果挤到屏幕下方 |
| 没有待处理事项 | “当前没有需要提醒的事项” + 常用能力 | 不制造紧迫感 |
| 数据不可用 | 说明哪类数据未取得，给重试/选择事项 | 不能用“没有待办”代替读取失败 |

## 4. 首屏信息层级

以下是内容线框，不是最终视觉稿。数值与名称均为设计示例。

```text
TeachBuddy                              [任务 2] [收起]
仅你可见 · 高二物理 3 班

现在可以处理
动量守恒 · 今天 19:00
已开课 10 分钟，3 人尚未进入课堂
可为这些同学分别准备私聊提醒
[生成 3 份提醒]                        [暂不处理]

还可以帮你
[个性化提醒 1] [课堂回顾 2] [错题再练] [学情总结]

告诉 TeachBuddy 你想做什么……
                                      [发送给 TeachBuddy]
```

视觉重点：身份、当前聊天和主事项清楚；事项标题和主动作最突出；正常状态不展示上下文来源、版本、刷新时间或“依据”信息；四项能力带可处理事项数量并保持紧凑，避免与主卡争夺主视觉；底部保留稳定输入区。影响操作的数据缺失或过期在发生时以业务文案提示，不让老师承担正常的上下文管理工作。

有任务时，该空间展示工作过程和产物。常用能力收为输入区旁的 `教学协作` 入口，不让四张大卡永久占据对话首位。连接正常不常驻技术说明；连接失败时再出现对应恢复提示。用“仅你可见”替换面向用户解释“同一教学 Agent”的工程身份文案。

### 4.1 次要事项：紧凑入口带数量，点击展开副卡

推荐保留一张主卡；下方能力入口使用内联小数字，如 `课堂回顾 2`、`个性化提醒 1`。点击后在同一区域展开具体事项，主卡压缩为一行可返回的摘要，避免同时出现多张高强调大卡。一次展开一个类别；收起后恢复主卡和紧凑入口。

例如展开 `课堂回顾 2`：

```text
课堂回顾 · 2 项可处理                         [收起]
上节课 · 机械波基础
课堂已结束，可准备课堂回顾                    [生成回顾]

上一节 · 动量守恒
课堂已结束，可准备课堂回顾                    [生成回顾]
```

老师点击副卡的生成按钮后自动带入课次和已知对象，直接发送自然语言任务要求给 TeachBuddy；正常路径不增加配置或二次提交。必要对象仍无法确定时，Agent 在同一对话里只补问缺少的项。数字告诉老师有具体事情可做，展开后必须能直接操作，不能只显示通用功能说明。

数量和强调建议：

- **普通机会用低强调数字，时效紧迫才飘红。** 两节课可生成回顾不等于两项逾期待办；课堂回顾用中性角标，临近截止或确已逾期且需要处理的事项才用红色，同时以“临近截止”等文字表达原因。
- **按可行动事项计数。** 课堂回顾 `2` 是两节符合条件的课；作业提醒 `1` 是一份需跟进的作业，展开后再显示涉及 6 人。不能混加课次数、学生数和未读消息数。
- **当前范围内计数。** 群聊为当前班级，私聊为当前学生有权使用的业务范围；不把其他班级事项混入当前入口。
- **计数只包含主卡之外的其他事项。** 主卡已展示的同一提醒不再算入次要数量；教师发起后该事项进入“任务”的真实状态，不继续作为一项未开始机会计数。
- **进入列表不等于完成。** 展开不会清零；明确暂不处理、事项已解决或任务已开始后才按相应状态移出可发起计数。待确认产物继续在“任务”中可找回。
- **已结课不是唯一条件。** 只计入有可用内容、在约定回顾范围内且尚未启动/完成该回顾的课次；已交付、无权限、资料未准备好的项目不累计成长期红点。具体历史窗口在场景数据里显式设定，待教师验证。
- **没有机会不显示 0。** 入口仍可手动发起；读取未完成或失败时也不把未知显示为 0，展开时给必要的读取状态。
- **工作中收纳。** `教学协作 · 3 项可处理` 汇总去重后的次要事项，点击展示各能力及数量；与顶部 `任务 2`（进行中/待确认工作）保持不同含义。数字变化不闪动、不抢焦点。

### 4.2 提醒学生与提醒老师处理作业

用户补充的“提醒批改某份作业”属于教师自己的待处理工作。建议在展开内容里明确分组：

- `学生需跟进`：词汇练习 · 4 人未提交 → `准备催交提醒`。
- `我需处理`：词汇练习 · 6 份待批改 → `去批改`。

教师待批改使用 `作业待办 1` 的紧凑副入口承接，不伪装成“提醒学生”的一项能力。同一份作业可在副卡内同时提供两个适用动作；汇总事项数按该业务事项去重。任务按钮仍写清由谁处理、处理什么。只有已核实可达的批改页面才提供 `去批改`，本轮不将它扩大为 AI 自动批改；尚不可达时保留为设计场景，不放可点击的空按钮。

自然语言入口始终可用。老师可直接说“先帮我提醒还没交的同学”，由系统识别当前事项；这不要求先点副卡，也不新增语音识别接入的承诺。

## 5. 教学时点驱动的提醒建议

| 教学现场 | 可信触发依据 | 首屏内容示例 | 下一步与默认交付 |
| --- | --- | --- | --- |
| 即将开课 | 有效课次、开课时间、未取消；尚无同事项有效提醒记录 | “今天 19:00 上课，还有 20 分钟，需要提醒大家提前进入吗？” | 准备全班开课提醒；默认当前群 |
| 已开课 | 实际开课事件、及时到课记录、应到名单，排除请假/已进入者 | “已开课 10 分钟，3 人尚未进入课堂” | 一键发起；系统自动核对名单并生成 3 份私聊提醒 |
| 刚下课 | 课次已结束、关联作业已正式发布且有提交要求 | “本讲作业已发布，明晚 20:00 截止” | 准备全班作业提醒，带作业入口 |
| 稍后返回 | 同份作业未完成状态与可信截止时间；有新的处理价值 | “距截止还有 3 小时，4 人尚未提交” | 一键生成私聊提醒，系统自动排除已经提交者 |

20 分钟、10 分钟、3 小时均为讨论样例，不是已锁定的系统阈值。课程有调整、延迟开课或提前结束时按业务状态修正；仅有课表时间不足以断言“课堂正在上课”。

“未进入”不等于旷课；未取得作答不等于不会；聊天中说“布置了作业”不等于已有可提交业务对象。刚下课却没有已发布作业时，引导“选择要提醒的学习任务”，不补造作业内容或截止时间。

截止前用“尚未提交”，截止后且状态核实时才显示“已过截止时间”。请假、延期、已提交待批改、已提醒的学生需要分别表达，不能合并为一个“未完成”标签。

### 5.1 自动加载与真实业务数据的可用性

当前项目的 DW 派生数据是冻结快照。用户已认可先使用延迟的业务底稿，再通过场景时间和事件投影模拟课前、课中、课后等体验；无需等待生产实时接口才开始前端验收。该加工不会把数据来源升级为生产实时，详细规则见下一节。

- 数据可用：自动读取并展示具体事项、人数和可执行动作，正常状态不常驻来源与更新时间。
- 真实数据确已过期或读取失败：先自动尝试更新；仍无法完成时显示“暂时无法确认谁已进入课堂”，提供“重试”或“一般开课提醒”等业务出口，不把上下文管理变成老师的日常操作。
- 权限不足：显示“暂无权限查看本班到课状态”；保留一般性提醒撰写能力。
- 多门课/多份作业无法唯一匹配：先让老师选择一项，不默认选第一项并隐式生成。

### 5.2 DW 派生数据与场景时间

采用 `授权业务范围内的完整底稿 → 去标识冻结副本 → 场景时间/事件加工 → 页面与 Agent 共用同一场景状态` 的路线。这里“全集”指选定机构、教师、班级和时间窗口内，能够闭合本次教学场景的关联数据；不扩展为导出整个数仓。

保留原始快照和采集时间，在独立场景副本上调整课次、作业截止、消息与事件的相对时间。缺少到课或提交日志时，可按固定规则补充模拟事件，但记录其模拟来源；不靠修改一个日期就把缺失事实补成“真实”。场景时钟允许重置并切换课前/课中/课后/回访，页面和 Agent 在同一时点只看到已经发生的事件。

正常产品面不展示“模拟数据”等开发提示；来源、原始时间、偏移和合成事件保存在内部证据及验收记录，遵循 D-109。该策略能支持完整交互演示，同时保留数据加工的可追溯性。本轮只完成已有投影的静态盘点与加工方案，未新增 DW 查询或生成已接入页面的数据集。

## 6. 快捷发起：一次点击即发送任务，自由提问是共同入口

用户已明确确认：主卡与副卡上的“生成”按钮，把系统准备任务意图和发送给 TeachBuddy 合并为一次操作。正常路径为 `点击生成 → 对话里出现这次要求 → Agent 处理 → 产物待确认`，不再停在预填输入框，也不再强制先填写一张准备表。

例如老师点击 `生成 3 份提醒`，在 AI 对话中立即出现一条可读要求：

> 帮我给这节课尚未进入的 3 位同学分别生成一条温和的私聊提醒，并附课堂入口。

系统同时自动携带当前会话、具体课次和对象引用。内部 Prompt、Skill 指令和数据装配过程不铺成教师的长发言；对话展示与按钮意图一致的自然语言要求。

老师直接输入“帮我提醒还没进来的同学”，进入同一条能力链路，按同一规则读取数据、生成、修改和审阅。卡片是可发现的任务表达捷径，底层可用 Skill 组织方法，但教师不需要进入 Skill 页面，也不要求用固定句式才能触发。当前实现仍需核对和接通统一分派，不能将设计中的 Skill 当成已安装能力。

细节规则：

- **信息完整直接生成。** 已知班级、课次和对象自动带入，无须老师确认“AI 已知道”。
- **信息缺失在对话里补问。** 有两份候选作业时只问“要提醒哪份作业？”，允许点选或文字回答，再继续原任务。生成失败不回退为假文案。
- **输入不被覆盖。** 老师已有未发送文字时，卡片命令独立提交，保留原输入；不把未提交草稿一并发送、不静默改写它。执行后可继续使用该草稿。
- **要求可继续修改。** 老师可追加“别催促，先问是否遇到困难”；对象或交付变化同步到实际任务，不能只改正文中的名字和人数。
- **动作可辨认。** `生成提醒`/`生成回顾`直接启动 AI；`查看名单`只查看，展开类别只导航；`去批改`打开业务页面，不假装调用生成能力。
- **防重复。** 同次点击只有一条任务提交；接受后按钮转为实际运行状态。Runtime 不支持同会话并发或排队时，应明确等待/继续路径，不创建虚假的排队事件。
- **生成与交付分开。** 一键提交给 AI 只授权处理和生成；向班级或学生发送仍经过产物审阅、对象与目的地确认和消息回执。

本次确认替代本文旧版两次操作的推荐，并针对 IM 卡片收窄替代 D-114 的预填不自动提交条款。D-121 的对象引用、最小证据和教师最终交付控制继续保留；已知对象不再要求前置人工重选。

### 6.1 其他顺手的发起方式

1. **从业务消息发起。** 在作业卡、课次卡操作中提供“生成提醒”，自动带入对象并提交任务；在普通消息上提供“交给 TeachBuddy”，默认引用原文，目标不明确时再询问。后续接入不侵入当前 Part 2 Write Set。
2. **从老师自己的话发起。** “帮我提醒还没交作业的同学”直接进入相同能力；有两份作业时只追问作业，不重复问已知班级，不强制弹出准备表。
3. **从结果继续。** 完成全班作业通知后，只在后续确有未提交情况时出现“跟进这份作业”，沿用业务对象重新读取现状。完成当下先提供“在群聊中查看”，不同时推销所有后续功能。

## 7. 私有协作、当前上下文与发送目的地

正常 UI 只持续表达教师需要理解和决定的内容：

| 位置 | 文案示例 | 所表达的事实 |
| --- | --- | --- |
| Sidecar 标题 | “仅你可见 · 高二物理 3 班” | 当前协作的可见性和来源会话 |
| 对话里的任务要求/必要补问 | 已提交的自然语言要求，或具体缺少的业务选择 | 明确时直接处理；仅有歧义时补问，无前置必填准备表 |
| 产物审阅面 | “准备发给：李明 · 私聊”或“发送至：高二物理 3 班 · 全群可见” | 内容实际交付对象与渠道 |

删除默认的“依据：……”一行，以及来源列表、Context 版本、捕获时间和“确认已加载”步骤。后台根据当前聊天和业务事项自动加载所需上下文；老师无需选择数据源或理解内部数据装配。

自动加载完成时不必额外显示常驻“准备就绪”。若需要等待，使用实际状态驱动的短提示；发生缺失、冲突或权限问题时才就具体业务提问，例如“这次要提醒哪份作业？”或“暂时无法确认到课名单”。来源与版本保留为内部审计事实，需要解释结果时可按需说明，不放回每次必经的准备面。发送目的地和业务对象仍保留，因为它们直接影响教师的操作决定。

普通 IM 输入框继续使用“发送”；AI 输入框使用“发送给 TeachBuddy”；生成按钮使用“生成提醒草稿”。首次不在群消息时间线插入虚构的 Agent 欢迎发言。

全班共同通知可在当前群发送。涉及个体未进入、未交或订正情况，推荐分别准备私聊草稿；当前没有稳定学生私聊关系时显示“无法匹配私聊对象”，允许老师修正对象，不转为在群里公布个人情况。

多人提醒是同一任务下的多份草稿，可统一改语气、逐人核对；不让老师手动重复创建三次任务。第一版可按“转到学生私聊并插入 → 老师发送 → 返回下一位”复用现有 Composer Gate。若后续做批量发送，必须另行规定逐条回执、部分失败和重试交互，不能把现有单人插入当作已有批量发送。

## 8. 切换聊天时保留工作的体验

原则：当前 Sidecar 跟随当前聊天；原任务保留来源和状态。相同教师从两种入口进入同一聊天，恢复同一任务现场。

### 8.1 需要保留的内容

- 尚未发送给 AI 的输入、已选事项、对象、老师补充要求；
- 已提交任务的真实运行状态、停止/失败事实与产物；
- 教师对产物的修改、当前审阅对象、尚未发送的版本；
- 消息交付回执及回到原消息的入口；
- 面板展开状态与关键阅读位置。

本 Session 内切换和关闭面板需完整恢复；页面刷新也应恢复文字、选择和已保存产物。图片附件跨刷新需要单独确定存储策略，未保存时明确提示重新添加。跨设备恢复留作后续能力，不用“已保存”暗示已经实现。

### 8.2 三个可见的恢复入口

1. 当前 Sidecar 标题 `任务 2`：只有存在任务时出现，展开轻量列表；各行显示“来源会话 · 事项 · 状态”。
2. 切换聊天后显示一条简短提示，例如“高二物理 3 班的提醒正在生成 · 查看”；多个任务聚合为数量，不堆叠横幅。
3. 有消息列表的聚合入口可给原会话附加“AI 生成中 / 待确认”次级状态。它表达老师私有任务，不计为学生消息未读。

点击“查看”返回原聊天及其任务；不把 A 群草稿直接铺到 B 群的输入框。返回学生私聊发送属于显式交付动作，需保留“返回原提醒任务”。

关闭面板或切换聊天不等于停止已提交的任务。仅当 Runtime 确认仍在运行才显示“生成中”；断线或无法核验时显示“正在同步任务状态”。完成后用轻提示“提醒草稿已准备好，待你确认”，不强制跳回原群。

一条 Thread 继续复用既有绑定 Session。任务列表显示该 Session 里的具体工作及产物状态，不引入第二套伪运行记录。同一 Session 正在生成时可以保留下一项的输入，但如 Runtime 不支持排队，不得显示“已排队执行”。

## 9. 主动提示的节制

新建议自动读取的合理时点：首次打开当前聊天、回到当前聊天、相关课次/作业状态变化。异常时允许老师重试，但不设置每次必经的“刷新上下文”。后台事件只更新可见状态，不自动生成消息或代表老师发送。

- 同一事项只有一个有效建议；已启动时显示“处理中”，不再给重复生成入口。
- “暂不处理”关闭本次建议；离开再回来不能立刻重新打扰。相关事项发生实质变化时可重新呈现事实，但是否重新吸引注意遵循关闭范围。
- 可提供“这次不提醒”和“关闭此类建议”的层次，后者也要可恢复。具体冷却时间与事件阈值待教师验证。
- 老师输入、选中文字、审阅或生成时，更新放在折叠入口里，不替换文本、不抢焦点、不自动滚动。
- 已通过本产品回执确认提醒过的对象不重复推荐；不能仅因老师手动发过一条类似消息就断言已完成全部提醒。
- 对象在准备时及交付前重新核对。3 人变成 2 人时显示“1 人已进入，已从建议名单移除”，由老师确认更新后的草稿；不静默发送旧名单。
- 未提交变 0 人时撤下催交主动作；现有草稿保留可查看，并标为无需再提醒。

## 10. 反馈要让老师看见真实工作

点击生成后立即展示对应的自然语言任务要求；读取慢时显示“正在核对到课名单”，只在实际读取中使用此状态。之后显示真实过程与耗时，可停止，失败保留完整要求。

结果采用可操作的成果区：`已准备 3 份提醒 · 待你确认`，先展示对象、渠道和第一份正文，允许切换对象。内容很长时使用现有放大审阅方式，不增加第四个永久栏。

发送反馈拆分为：

- “已插入回复框”：还没有发送；
- “已发送”：有消息回执；
- “已读”：仅消息服务确有读回执时展示；
- “已进入课堂 / 已交作业”：仅新的业务状态支持时展示。

不能将发送成功视为问题解决，也不将 AI 生成成功视为消息发送成功。未知发送结果先查回执，失败重试只针对确定失败的对象。

## 11. 当前代码与提案差距

本节为 2026-09-09 静态检查；未做本轮浏览器回归。

- `ImSidecarAgentSurface.tsx` 当前先显示四项能力配置和固定建议，再展示对话；缺少依据教学时点排序的主事项。
- 该组件用本地 `useState` 保存 `composerDraft`、`selection`、`messageDraft`、`learningArtifact` 和 `delivery`。
- `WorkBuddyImSidecar.tsx` 给该组件设置随目标变化的 `key`，切换会话会重建组件。
- `im-agent-session-binding.ts` 持久记录只有 `sessionRef` 和 `updatedAt`。因此 Session 恢复不能证明未提交输入、选择和编辑状态已恢复。
- 当前真实 Runtime 和过程反馈可继续复用；跨聊天后台观察、完整工作状态保存、事件驱动建议与多人审阅仍需专门实现与验收。

以上差距不自动扩大为本轮修复。详细契约、持久策略和测试在体验讨论收敛后更新 Feature Spec。

## 12. 验收场景与推进顺序

首轮前端实现建议选择“开课 10 分钟，3 人尚未进入”作为主演示，固定场景可切换课前、刚下课和稍后催交，用同一能力链路检验卡片与自由输入的一致性。演示数据的内部证据保留真值，按 D-109 不在正常产品 UI 堆放开发徽标。

验收需包含：

1. 初次进入两种入口，教师能解释助手能做什么、谁能看到内容，且不重复新手引导。
2. 四个教学时点出现不同依据和动作；实时数据不可用时不虚构“当前缺勤”。
3. 主卡/副卡点击一次生成即提交任务，没有预填后二次提交；自然语言触发同一能力；既有未提交输入不被覆盖或误发。
4. 生成期间切到另一聊天，能看到原任务状态；回来后任务和产物完整。
5. 未提交要求与已编辑草稿切换回来仍保留；页面刷新按规定恢复。
6. 群里发起个体提醒，目的地始终清楚；个人状态不会因为当前处于群聊而公开。
7. 名单从 3 人变 2 人、所有人完成、作业延期、权限撤销时能正确恢复处理。
8. 忽略建议后反复进出聊天不重复打扰；生成失败和状态断线有清楚出口。
9. 宽屏、班级窗口、键盘导航、焦点恢复均无遮挡和不可达操作；状态通知采用可访问文本。
10. 已插入、已发送、已读、业务完成的区别由真实证据支撑。
11. 次要入口的数字与展开后的可处理事项一致；主卡去重、已生成转任务、已完成移出等转换不重复计数；普通回顾机会不会全部飘红。
12. 正常路径没有强制准备表、“依据”或上下文确认步骤；后台自动加载，异常只询问必要业务问题。
13. DW 派生场景支持固定时钟与重置；页面人数、角标、名单和 Agent 输入一致；未来提交/到课事件不会泄漏到较早的场景时点。

推进顺序：先完成真实底稿采集，再构造场景；按首屏一键发起、对话补问、群体提醒审阅/交付的连续体验更新 Spec、拆分 Write Set 并实现。其他三项复用自动上下文、任务恢复、成果审阅和反馈；各自保留业务特有证据与产物结构。
