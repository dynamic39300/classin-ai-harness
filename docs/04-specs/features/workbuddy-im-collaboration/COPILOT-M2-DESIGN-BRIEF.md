# IM Copilot M2 重启设计输入基线

## 1. 本文是什么

本文用于界定 M2 重做范围，不替代上午形成并经用户补充修订的[情境引导体验提案 v1.2](./COPILOT-CONTEXTUAL-ENTRY-EXPERIENCE-PROPOSAL.md)。体验提案保留原文和当时的设计推理；本文只说明哪些下午线框产出已经撤回，以及重做时仍需遵守哪些事实和原则。它不继承已撤回线框稿的视觉与结构答案。

2026-09-09，用户判断下午两轮线框页面的线上效果和真实教学感均不理想，要求清空这部分设计稿、由其派生的交互说明、开发态原型与对应验收，重新开始 M2。用户随后明确：上午的体验提案和数据采集方案都应完整保留。具体范围见 D-133，总体状态见[里程碑计划](./COPILOT-MILESTONE-PLAN.md)。

## 2. 需要解决的真实问题

ClassIn 原有 IM 以教师与学生直接沟通为主，包括班级群聊、学生私聊、文字、文件和附件。教师既可以从班级页面进入聊天，也可以从首页“消息”进入聚合消息列表；两个入口最终指向同一套群聊或私聊。

TeachBuddy 进入 IM 后，需要让教师在不学习技术概念的前提下明白三件事：

1. 它能结合当前教学现场帮助自己做什么；
2. 自己可以像聊天一样表达要求，并和 AI 一起把面向学生的话术准备好；
3. AI 的建议、生成与正式发给学生是不同动作，最终交付仍由教师控制。

当前失败不在于这个产品问题不存在，而在于过早用固定线框和薄场景替代了设计推理。页面能点击，但信息层级、交互节奏和教学真实感不足，不能作为下一阶段实现依据。

## 3. 保留的产品定位

- TeachBuddy 是教师在 IM 内的私有教学协作助手，界面简称 TeachBuddy；教师无需选择内部 Agent、Skill、MCP 或模型。
- 核心价值是通过沟通理解教师意图，结合教学上下文生成、修改和准备沟通内容，而不是让教师管理一套复杂的 AI 任务系统。
- 快捷入口可以帮助教师更快说出需求，自由表达始终是完整入口。快捷入口背后调用能力，但不要求教师理解 Prompt 或 Skill。
- 已知的班级、课程、课次、作业和当前聊天上下文默认由系统加载。只有缺失或真实歧义阻碍继续时，AI 才需要向教师补问。
- 教师与 TeachBuddy 的协作默认仅教师可见。发送给班级群或学生私聊前，应让教师清楚知道内容与目的地，并由教师作最后确认。
- 群内公开 Agent 与人与 Agent 私聊属于后续独立设计，不在本次 M2 中混入教师私有 Copilot。

## 4. 保留的体验问题与引导理念

### 4.1 第一次发现

教师第一次在熟悉的 IM 里看到 TeachBuddy 时，需要快速理解入口、能力范围和使用方式。设计需要回答从哪里打开、第一次看到什么、什么时机出现引导，以及关闭后如何再次找到。具体采用自动展开、入口提示、首屏说明或其他方式，重新设计，不沿用旧稿答案。

### 4.2 与教学现场相关

引导需要与当前教学进度有关，而不是展示抽象能力目录。至少覆盖四类教学时点：

- 即将开课：帮助教师准备提前进入课堂的提醒；
- 已开课：存在尚未进入课堂的学生时，帮助教师准备有针对性的沟通；
- 刚下课：作业已经明确发布时，帮助教师准备全班任务通知；
- 稍后回访：部分学生仍未提交时，帮助教师准备催交，同时区分学生待完成和教师待批改。

这些是设计场景，不是生产阈值。是否提醒、人数、时间、请假与完成状态必须来自可核实数据，未知不能展示为 0 或确定事实。

### 4.3 主次与克制

教师在某一时刻通常只有一个最值得处理的事项，其他机会应降低视觉权重，但仍可被发现。次要事项可能需要数量提示，例如可回顾课堂数或待跟进作业数。主次关系和计数语义需要保留；是否用主卡、副卡、角标或其他视觉形式，重新设计。

### 4.4 以沟通完成协作

教师应能直接说“提醒还没交作业的同学”“第二门课程”“语气温和一点”来推进工作。AI 可以在沟通过程中提出必要问题，也可以提供便于回答的选项；选项是辅助，不应把教师推入反复选择对象、任务和页面的流程。

这是交互目标，不预先锁定为某种对话气泡、卡片组合或固定页面结构。下一版需要先用完整用户旅程和对话脚本证明逻辑，再决定界面承载。

### 4.5 与 IM 的关系

设计需要清楚说明 TeachBuddy 的私有协作与班级群聊、学生私聊之间的关系，以及内容如何从协作产物进入正式 IM。切换群聊和私聊后，未完成的协作不应丢失或串到错误班级；恢复方式、保存范围和目的地提示需要在新 M2 中重新推导。

## 5. 不可丢失的业务事实

```text
教师
└── 多个班级
    ├── 一个班级群
    ├── 多门课程
    │   ├── 各自的课次与教学进度
    │   └── 各自的作业、提交与批改状态
    └── 同一批学生可参与多门课程
```

提醒必须定位到“教师 → 班级 → 班级内课程 → 具体课次或作业”。同一学生在课程甲完成，不代表在课程乙完成；同一班的不同课程共用班级群，不因此创建多个群。该事实由 D-131 与 DW 结构研究支撑，不属于被撤回的页面方案。

## 6. 数据事实与后续开发门槛

仓库并非完全没有数据：M0/M1 已保存一轮 DW 只读采集、去标识冻结底稿和可重置场景投影。但当前数据仍有课程名称、完整群成员、真实私聊关系、实时请假/到课、课堂内容和历史交付回执等缺口；部分事件和第二课程关系是明确模拟。因此，M1 可以作为业务研究与场景证据，不能单独证明页面已经模拟了真实使用。

前端样式与交互实现开始前，需要把“可用于体验开发的真实模拟数据”定义为：来源可追溯、身份已去除、范围完整、时间可重置、原始事实与模拟补充逐项区分，并能通过同一 Adapter 向页面和 Agent 提供一致的班级、课程、课次、作业、学生状态、消息上下文及交付状态。具体 Gate 由[数据准备方案](./COPILOT-DW-SCENARIO-DATA-PLAN.md)维护。

## 7. 明确撤回的内容

以下内容全部归零，不能在新 M2 中被默认继承：

- 两轮线框页面及开发态 query 入口；
- 已画出的 Sidecar 页面结构、卡片组合、任务计数、任务列表、二级页和返回关系；
- 已写定的按钮位置、字段排布、精确文案、宽窄屏承载与草稿卡样式；
- 为固定线框编写的有限意图解析、状态保存与模拟生成代码；
- 旧线框的浏览器检查、技术验收和“可点击稿已交付”结论；
- 以下午旧线框为前提的 M2 详细交互说明。

上午的[情境引导体验提案 v1.2](./COPILOT-CONTEXTUAL-ENTRY-EXPERIENCE-PROPOSAL.md)予以保留，并继续作为上游设计背景；其中明确标为推荐或待验证的内容仍需在新 M2 中评审，不能直接解释为最终页面答案。研究资料中的竞品事实、用户原始反馈和数据事实继续保留。

## 8. M2 重新开始的交付方式

M2 当前只交付设计文档，不制作线框页面或前端交互。新的设计文档需要按顺序把以下内容说明清楚：

1. 核心用户故事与完整使用旅程；
2. Copilot 与 IM 的信息架构和边界；
3. 从发现、发起、沟通、生成、修改到交付和恢复的交互逻辑；
4. 页面区域、元素职责、显示条件和信息层级；
5. 正常、空白、权限变化和对象变化怎样影响统一教学动态，以及生成中、需补充、待确认、失败和完成怎样留在对应对话与产物中；
6. 四个教学时点及班级内多课程的内容与数据映射；
7. 关键文案原则、可访问性和较窄窗口规则；
8. 未决问题、设计取舍和可逐项评审的验收清单。

这份文档经用户审阅收敛后，才进入实施拆分。前端页面样式、真实交互和可点击验收放到后续开发里程碑，并以满足数据 Gate 的可重置模拟数据驱动。
