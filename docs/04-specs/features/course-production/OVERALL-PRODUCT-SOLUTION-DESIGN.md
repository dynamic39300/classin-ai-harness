# 课程目标到课程对象整体产品方案设计

## 1. 文档定位

本文是 WorkBuddy 首条业务切片“课程目标到课程对象”的整体产品方案设计事实源。它回答的是：这一条业务闭环要为教师完成什么结果、由谁在什么范围内使用、系统读取和产出什么、AI 能力如何参与、教师在哪里控制、哪些动作会改变业务，以及如何判断业务真的完成。

本文处于“产品方案设计”阶段，不是 PRD、Feature Spec、UI 视觉稿或 Agent Runtime 设计。它先把产品边界和业务链路讲完整，再为后续交互原型、Feature Spec 和工程实施提供稳定输入。

## 2. 当前阶段结论

### 2.1 要做的业务结果

教师输入一个教学目标和基本约束，WorkBuddy 通过目标澄清、上下文组织、课程结构生成和教师审教，形成一份可修订、可比较、可确认，并可模拟保存为课程/单元/活动草稿的**可审教课程方案包**。

第一版的业务闭环是：

```text
目标与约束
→ 范围与成功标准确认
→ 授权上下文与依据
→ 课程方案包初稿
→ 整体/单元/活动审教
→ 审教意见与修改
→ 新版本与差异
→ 再次审教
→ 规则校验
→ 最终确认
→ 保存审批
→ 模拟写回与执行回执
→ 结果复查与评价
```

### 2.2 第一版不做什么

- 不生产具体 PPT 文件，不做页面级排版；
- 不制作图片、动画、视频等多媒体素材；
- 不连接真实 ClassIn API，不执行正式发布；
- 不直接判断真实学生学习结果，不修改成绩或提交状态；
- 不做多教师协作、跨机构批量处理和跨天自动调度。

### 2.3 第二版如何扩展

第二版从第一版最终确认的课程方案包派生 `PPT 课件 Artifact`，再增加页面/章节/活动级课件审教、课件版本比较和课件确认。第二版复用第一版的目标、Context、来源、教师控制、审教意见、版本和确认机制，不重建一条孤立的课件生产链。

## 3. 七个设计层次总览

七个层次是产品设计需要回答的问题，不是七个页面，也不是七个技术模块。每个层次都必须有明确结论、输入来源、输出物、教师控制和验收方式。

| 层次 | 产品问题 | 本切片的设计结论 | 主要产出 |
| --- | --- | --- | --- |
| 1 | 要帮教师完成什么结果？ | 完成可审教、可确认、可模拟保存的课程方案包 | 业务目标、范围、成功条件 |
| 2 | 谁在什么情况下使用？ | 单教师、单机构、单班级课程、单次 WorkBuddy Run | 角色、入口、前置条件 |
| 3 | 系统读取和产出什么？ | 四类输入进入有来源的 Context，输出分为草稿、控制事件和业务回执 | 对象、证据、事实所有权 |
| 4 | AI 怎样一步步完成？ | 目标澄清、依据构建、结构生成、审教修订、完整性检查组成能力链 | AI 编排步骤、Skill 输出 |
| 5 | 教师在哪里参与？ | 教师确认目标、审教方案、处理意见、确认版本、审批保存 | 操作流程、信息架构、控制点 |
| 6 | 哪些动作会改变业务？ | 方案包生成不改变 ClassIn；审批后的 ProposedAction 才允许模拟写回 | 状态、权限、异常、恢复 |
| 7 | 怎么判断真的有帮助？ | 同时评价产物质量、教师控制、执行可靠性和业务价值 | 指标、评价事件、验收门槛 |

## 4. 七层产品方案详解

### 4.1 业务结果与范围

WorkBuddy 的职责不是替教师决定教学目标，而是把教师意图组织成一份可被专业审教的课程方案包。业务完成必须同时满足：教师确认目标和成功标准；方案包包含课程范围、单元、课时/活动、评价和资源建议；至少完成一轮审教；规则校验通过；教师明确确认最终版本；保存动作经过审批并返回执行回执。

### 4.2 用户、业务时刻与使用范围

| 项目 | 第一版定义 |
| --- | --- |
| 发起者 | 教师 |
| 主要影响者 | 教师；学生只作为课程设计的潜在教学对象 |
| 业务时刻 | 教师已有课程目标，需要形成课程结构和可执行安排 |
| 入口 | 统一 WorkBuddy 工作台中的“把课程目标整理成课程方案” |
| 组织范围 | 单机构 |
| 教学范围 | 单班级课程 |
| 运行范围 | 单次 WorkBuddy Run |
| 正式业务对象 | ClassIn 课程、单元、活动事实 |
| WorkBuddy 产物 | 课程方案包、审教意见、版本、待确认动作和评价事件 |

开始前至少需要教师身份、机构范围、课程范围、年级/学段、预计课时和可理解的目标描述。关键输入不足时进入 `needs-input`，不能生成看似完整的方案。

### 4.3 四类输入、输出与事实所有权

| 输入类别 | 典型内容 | 产品处理 | 事实所有者 |
| --- | --- | --- | --- |
| 产品逻辑 | 流程、审教颗粒度、确认和结束条件 | 形成界面流程和状态约束 | WorkBuddy 产品设计 |
| 业务规则 | 权限、课时约束、版本冲突、写回审批 | 形成阻断项、策略和动作门槛 | ClassIn 领域/机构规则 |
| Domain Knowledge | 课程标准、叙事写作进阶、活动设计原则、评价量表 | 作为有来源的依据进入 ContextSnapshot | Knowledge 系统 |
| 业务数据与 API | 教师、机构、班级课程、课程版本、已有结构和保存接口 | 只读读取，写回通过 Adapter | ClassIn 领域 |

运行信号（缺口、权限拒绝、冲突、超时和回执）是贯穿运行期间的控制证据，不替代四类输入。

主要输出分为三组：`GoalIntentDraft`、`ContextSnapshot`、`ArtifactDraft` 和 `ReviewComment` 是 WorkBuddy 可追溯产物；`ProposedAction`、`Approval` 和评价事件记录教师控制；`ExecutionReceipt` 记录课程/单元/活动草稿写回结果。

### 4.4 AI 能力链与 Skill 组合

产品层先定义业务步骤和能力契约，不在此阶段锁定模型、Prompt、MCP、A2A 或具体 Agent Runtime。

| 步骤 | 产品能力 | 输入 | 输出 | 必要控制 |
| --- | --- | --- | --- | --- |
| 1 | 目标澄清 | 原始目标、年级、课时和约束 | `GoalIntentDraft` 或缺口清单 | 教师确认目标和成功标准 |
| 2 | 依据构建 | 业务范围、课程事实、Domain Knowledge | `ContextSnapshot` | 展示来源、版本和授权范围 |
| 3 | 课程结构生成 | 已确认目标、Context、课时约束 | `ArtifactDraft v1` | 检查目标覆盖、课时和结构 |
| 4 | 结构化审教 | 方案包、来源、目标和评价 | `ReviewComment[]` | 教师指定范围、严重程度和依据 |
| 5 | 方案包修订 | 当前版本、指定意见和教师指令 | 新版本、Diff、意见处理结果 | AI 只处理明确指定范围 |
| 6 | 完整性校验 | 当前方案包、意见、来源和课时 | `ValidationReport` | 阻断项未清零不能确认 |
| 7 | 保存动作准备 | 最终确认稿、对象范围、expectedVersion | `ProposedAction` | 展示风险、范围和版本 |
| 8 | 写回与评价 | Approval、Adapter 结果 | `ExecutionReceipt`、`EvaluationEvent` | 不把部分成功汇报为整体成功 |

第一版 Skill 只覆盖目标澄清、课程结构生成、方案包修订和方案完整性检查。审教、审批、权限判断和写回属于产品流程与业务控制，不应伪装成 Skill。

### 4.5 教师体验、操作流程与控制点

教师体验由目标与对话区、方案包工作区、依据与版本区、控制与回执区组成。主流程为：

```text
选择任务 → 输入目标与范围 → 补充缺口 → 查看初稿 → 整体/单元/活动审教
→ 逐条处理意见 → 人工修改或 AI 定向修改 → 查看 Diff → 再次审教
→ 规则校验 → 确认最终版本 → 审批保存 → 查看逐项回执
```

教师拥有目标确认、依据查看、意见创建与处理、版本选择、人工接管、最终确认、审批、拒绝、退回、重试和继续编辑权。AI 不自动关闭审教意见，也不自动把草稿变成正式业务对象。

### 4.6 业务副作用、状态与异常恢复

方案包生成、修订和审教只影响 WorkBuddy 产物。只有最终确认后的 `ProposedAction` 在教师 `Approval` 之后，才允许进入模拟 ClassIn Adapter。

```text
空白 → 需要补充 → 生成中 → 待审教 → 待修订 → 待再次审教
→ 待最终确认 → 待审批 → 执行中 → 已完成待复查
```

信息不足、生成失败、版本冲突、权限拒绝、部分成功和页面关闭都必须保留上下文并提供恢复路径。第一版真值统一为 `SIMULATED`，真实连接和正式发布不在当前方案内。

### 4.7 验收、评价与业务价值

评价分为产物质量、教师控制、执行可靠性和业务价值四层，分别关注目标覆盖与结构完整性、审教与确认行为、写回回执与恢复能力、教师耗时与后续使用。业务成功的最低证据是“教师最终确认 + Adapter 执行回执”，模型生成成功不是业务成功。

## 6. 版本边界与后续阶段

第一版只交付可审教课程方案包；第二版从最终确认方案包派生 PPT 课件 Artifact。当前不提前决定 Agent 拆分、模型和 Prompt、数据库与 Durable Runtime、真实 API 认证发布、PPT 模板和视觉规范。

产品方案确认后的标准顺序是：

```text
整体产品方案评审 → 详细交互与状态原型 → Feature Spec
→ 工程模块与接口拆解 → 纵向 tickets → 代码实施与验收
```
