# Copilot 真实 API、业务上下文与模型回答独立审阅台方案

> 2026-09-16 用户补充已实施：人工主评问答匹配、相关性和质量；工具、接口、字段技术核验由工程侧负责。增加业务语言的未调用信息候选，可反馈建议补充/暂不需要/需要讨论。以下原方案中的四维技术审阅要求由[当前合同](./review-lab/FEATURE-SPEC.md)覆盖。

## 1. 目标与当前安排

按用户 2026-09-16 的要求，在接入现有 Demo 前，建设独立测试页面，逐题展示接口、真实返回、实际模型输入、实际模型输出，并支持用户备注和复测。真实 API 返回的是当前教师、班级、课程、学生和教学活动的个性化业务依据；模型的通用知识不能替代这些事实。

用户已审阅同意本方案，批准先实施 A2、C2、E2、F1 四题。补充要求：第一阶段真实展示模型识别意图、选择 Tools 的取数计划，以及实际工具/API 调用与计划差异；后续增加开放式提问入口。工具选择属于模型路由，MCP 属于工具接入协议，两者分别标记。实施见 [第一阶段 PRD](./review-lab/PRD.md) → [Spec](./review-lab/FEATURE-SPEC.md) → [Tickets](./review-lab/TICKETS.md)。

建议建设可持续审阅的本地工具，独立目录、启动命令和服务端口，不依赖现有 Demo 的页面或进程。测试工具读取限定测试环境，通过本地服务端调用模型并存储审阅记录。实施前按 PRD → Feature Spec → Tickets 记录具体目录、接口合同和 Write Set。

完成本阶段的标志是：每个问题都有可追溯的测试记录、明确的支持范围、用户审阅意见和处理结果；据此形成后续真实接入清单。未通过的问题保留缺口，不影响审阅其他问题。

## 2. 每题展示六部分

左侧列出六组全部 21 个问题及进度；主区按下表展开；备注固定在当前问题内，并可定位到具体字段、上下文或回答片段。工程信息在此专用审阅台中展示。

| 部分 | 展示内容 | 审阅要回答的问题 |
| --- | --- | --- |
| 问题和业务范围 | 原始问题、选择的班级/课程/课节/活动/学生、时间范围、回答给老师还是生成消息草稿 | 问的是哪个对象、哪个时段？是否存在多种解释？ |
| 模型工具选择计划 | 真实模型提出的工具名、业务目的、预期字段、参数与工具到业务 API 的映射 | 模型选对工具了吗？是否多取、漏取、选错对象？ |
| 实际接口调用 | 方法、路径/协议命令、业务参数、调用顺序、每个接口的用途、请求时间、业务成功/失败；区分计划调用和实际执行 | 找对接口了吗？对象关联是否正确？ |
| 真实响应与字段 | 可展开的原始业务 JSON；字段路径、类型、值、含义、单位、枚举依据、字段来源；分页和覆盖范围 | 字段解释准确吗？真实的 0、空、缺失、未批是否被区分？ |
| 实际模型输入 | 规范化业务上下文、纳入/排除字段及原因、统计规则、缺口、最终发送给模型的消息与业务附件 | 模型真正拿到了什么？有遗漏、混入或错误推导吗？ |
| 实际模型输出 | 本次真实回答/草稿、关键事实的来源链接、模型与提示版本、耗时；没有运行时显示未运行 | 回答事实正确吗？满足老师的问题吗？ |
| 审阅与复测 | 数据正确、上下文够用、回答合格三个独立结论；备注、异议、处理说明、修订前后差异 | 问题出在数据、映射、规则还是表达？修订是否解决？ |

凭据、Cookie、报告票据和签名下载链接只留服务端。展示脱敏时标明替换位置，保持字段结构和对象关联；业务原文在授权本地审阅范围内可检查。真实响应、脱敏副本和演示数据有独立来源标记。

接口示例、观察到的字段结构和正式契约分别呈现：单次样本不能证明字段永远必填、枚举已穷尽或所有状态都覆盖；空数组不能据此推断成员字段。枚举未核实的值直接标为待核实。

## 3. 让测试可以定位错误

### 3.1 保存原始响应与实际模型输入之间的映射

每个上下文字段能够追溯到某次响应的具体路径。派生统计另外保存公式、对象集合、时间范围和分母。业务规则由文档或已审阅规则支持，不能仅依据字段名称猜测。

例如 C2“这份作业还有谁没交，交上来的批完了吗？”：

1. 先用活动目录确认作业，再读取 `/lms/app/activity/homework/get` 和 `/lms/app/activity/homework/students`；只有需要单生提交内容时再读取 `/lms/app/activity/homework/student/detail`。
2. 核对实际分配对象、提交状态、批阅状态与更新时间。班级总名单不能直接替代本作业分配名单。
3. 用已核实的规则生成未提交、已提交待批、已批阅等集合，保留规则与响应路径。未知状态进入单独集合，不能凑入某一类别。
4. 让模型只根据这些事实回答；点击人数或学生引用可以回到证据。完整性不足时回答限定范围。

本例说明验证步骤，没有虚构人数、响应 JSON 或本次模型输出。课堂采集中的 `correctTotal` 曾随批改变化，必须核清语义后才映射为“已批/待批”。

### 3.2 同一份真实数据可以复测

提供两个明确模式：

- **实时读取**：重新调用业务接口，保存新的数据快照、读取区间和业务时间。跨接口读取未必是同一时刻，状态冲突时记录差异并重新核对。
- **固定快照复测**：使用已经捕获的真实响应，固定业务对象、时间语义和问题，再运行上下文转换和模型生成。页面显示原始采集时间，不能称为当前实时数据。

模型调用默认绑定已保存快照，不在生成中隐式补取未展示的业务数据。若后续支持模型按需取数，所有新增调用及返回都必须进入同一次可审阅记录。

每次运行保存问题版本、快照标识、字段映射/规则版本、提示内容、模型标识及可获得的参数、输出和错误。固定输入允许比较改动效果，但不保证模型每次文字完全一致。首次运行以新会话隔离其他问题；E5“整理刚才的内容”显式绑定上游回答和证据。

### 3.3 事实溯源与业务对照共同验收

模型输出关键事实时给出来源引用；系统验证引用确实存在，人工核对引用能否支持结论。仅有引用并不意味着结论正确，也不展示模型内部思维链。

为每个案例预先记录“应包含的事实、允许的推断、需要说明的缺口、不得作出的结论”。业务事实尽量与同对象、同时间附近的 ClassIn 教师/学生页面或已核实记录对照；原页面若使用同一个接口，只算一致性证据，不作为独立真值证明。

统计、去重、时间过滤和枚举映射优先由可检查的规则完成；模型主要解释、组织和表达。班级和课程分别绑定，跨课程分别展示；事实、AI 授课分析、聊天发言和建议分别标识来源。

## 4. 问题清单与执行顺序

全量清单采用现有[21 个问题定义](../../../../src/domain/workbuddy/general-question-guidance.ts)，保留 A1～F3 的既有 ID，六组全部展示。当前问题的接口候选及证据见[整体判断](./CLASSIN-REAL-TEST-API-OVERALL-ASSESSMENT-2026-09-16.md)；该文档中的“完整/可接”是待逐题验证的输入判断，不自动转换成审阅通过。

建议先用四个代表性问题验证工具，再覆盖全部问题：

| 顺序 | 问题 | 主要验证内容 |
| --- | --- | --- |
| 1 | A2 下一课时间 | 对象定位、真实日期、时间过滤、简单事实回答 |
| 2 | C2 作业未交与批阅 | 多接口关联、分配名单、状态语义、人数核对 |
| 3 | E2 课堂回顾 | 正式事实、笔记与生成分析的分层；证据缺失和冲突处理 |
| 4 | F1 两天聊天总结 | 群归属、时间窗、历史分页完整性、消息正文作为待分析数据 |

后续逐题增加正常、空/缺失、部分返回或权限失败等适用案例，并覆盖关键业务边界：未提交与待批、0 分与未评分、课中与课后、多课程与重名对象。可先用真实捕获快照开展审阅；实时调用未打通时单列阻塞。人工构造的边界样本明确标为构造测试，不计为真实调用通过。

实时考勤 B1 需区分课中/课后，当前成员级成功样本仍待补；F1 不能把读取到的少量消息当两天全集；E2 没有 ASR 正文时只能依据实际报告/笔记生成受限回顾。给家长或群内回复先测试草稿，发送验收另行进行。

## 5. 备注如何形成共识

审阅结论绑定“问题 + 案例 + 运行版本”，支持草稿保存、刷新恢复及导出 Markdown/JSON。问题整体结论必须注明已经覆盖哪些场景。

三个维度分别使用“待审阅 / 通过 / 需补充 / 有异议 / 不适用”，并记录原因：

1. **数据正确**：接口、对象、返回和字段含义核实；
2. **上下文够用**：回答所需事实、规则和范围齐备，已知缺口明确；
3. **回答合格**：模型实际输出忠于事实、满足问题，且表达可用。

备注可以提出错误、缺字段、规则分歧或输出偏好。后续修订关联原备注并记录依据；Agent 完成修改后标记“待复审”，保留用户原话和异议。用户确认后才记录为达成共识。输入或规则变化时，旧审阅记录继续保留，新运行明确显示变化及待复核部分。

用户修正的字段解释先作为建议规则保存，经证据核实再进入映射；原始响应不被备注覆盖。模型不得通过改写接口样本来迎合预期答案。

## 6. 用实测结果替换覆盖率估计

此前“约 90%”是对已识别数据路径的工程估计，没有逐题端到端验收分子，不作为已验证准确率。本工具分别报告：

- 已定位数据来源的问题数 / 21；
- 已有真实响应并完成业务核对的问题数 / 21；
- 上下文充分性已审阅通过的问题数 / 21；
- 真实模型回答已审阅通过的问题数 / 21。

同时展示案例通过数/总案例数、部分通过和阻塞数量，避免一个正常样本掩盖状态边界。E5 消息整理依赖已确认的上游上下文，不要求为每题人为增加新 API；仍需验证前文继承和生成结果。接口数量与问题数量是不同口径，不能相互换算。

首轮接入候选要求：适用案例的数据、上下文和回答均通过，必要依赖有证据，没有影响结论的未解决异议；只覆盖部分场景则明确限定接入范围。模型文风可以另记偏好，不与数据真实性混算。

## 7. 交付物与实施完成条件

1. 独立可启动的本地审阅页面，全部 21 题可选择；每题能看到已验证证据和待补项。
2. 真实只读接口调用与捕获快照回放；HTTP 200 与业务成功分开判断，空、权限、过期凭据、部分成功和失败可区分并重试。
3. 可检查的原始业务响应、字段语义、上下文映射及实际模型输入；每题仅纳入相关且获授权的数据。
4. 真实模型运行、失败重试和版本比较；未调用模型时明确显示未运行，手写示例不冒充生成结果。
5. 持久化备注、分歧处理和复审记录；私有样本和原始输出位于受限运行目录，导出共享文档使用脱敏内容。
6. 验证保存恢复、字段溯源、已知统计结果、身份/对象隔离和代表性模型事实错误；页面验收覆盖加载、空、错误与可恢复状态。
7. 导出逐题共识表、缺口清单及获准接入范围，作为后续真实接入 PRD 的输入。

第一阶段实现与验证以链接的 PRD、Spec、Tickets 及验收记录为准。模型选工具、执行器检查与 API 路由分别留痕；后续开放式提问复用此流程。
