# WorkBuddy 核心业务闭环与能力优先矩阵

## 文档定位

本文是 WorkBuddy 的全局业务场景、AI 能力分布和工程优先级总表。它把 AgentIn 参考资料中的业务闭环与 WorkBuddy 已有的能力矩阵对齐，并明确三种不同层级：

1. **单点能力**：一次调用完成生成、识别、转换、检索、解释或检查。
2. **组合能力**：多个 Skill、Tool 和校验步骤围绕一个业务对象协作，产出可编辑 Artifact 或判断草稿。
3. **完整业务闭环**：从教师目标出发，经过证据、产物、教师确认、业务写回和结果复查，形成可观察的业务结果链。

矩阵不把所有能力都缩减为四条首期切片。全量部分表达 WorkBuddy 的产品边界；优先级部分表达当前建议的工程实施顺序。内部追踪 ID 只用于工程定位，教师和产品对外使用“业务场景名称”。

## 一、统一业务定位

WorkBuddy 的核心不是若干孤立的 AI 功能，也不是让教师选择一组内部 Agent。它是统一教师工作台和主 Agent，围绕教师教学闭环组织 AI 能力，并把结果回到 ClassIn 已有的课程、课堂、作业、待办、消息、洞察和成长对象。

三条核心业务结果链是：

```text
作业与结果证据 → 错因分析 → 订正练习 → 学生完成与复查
备课演练证据 → 可观察反馈 → 课件/活动改进 → 再次演练对比
学情与课堂/作业证据 → 诊断假设 → 个性化干预 → 结果复查
```

“课程目标 → 课程对象”是课程生产基础链，也是当前锁定的第一条工程纵向切片。它为三条核心结果链提供目标、内容、活动和评价标准等上游结构。

## 二、从业务时刻到工程切片

```text
业务时刻地图
  → 产品业务闭环
  → 单点能力 / 组合能力
  → Skill / Tool / Module
  → 工程纵向切片
```

业务时刻是教师工作的完整地图，不等于页面；业务闭环是需要对结果负责的跨模块链路；能力点是可复用的 AI 方法；工程切片是可以从 UI 走到回执并被验证的交付单元。

学生侧能力是上述教师闭环的结果承接面：学生理解目标、完成练习、获得提示、订正并产生新的学习证据。学生侧不另建一套与教师业务事实冲突的状态，正式任务、提交和成绩仍由 ClassIn 领域拥有。

## 五、四条优先工程纵向切片

战略优先级与工程落地顺序必须分开表达：战略上最有价值的是三条核心结果链；工程上先用课程生产基础链建立可复用 Harness 样板，再逐步增加学生证据、媒体证据和跨对象副作用。

| 工程顺序 | 业务场景名称 | 业务价值链 | 首期交付边界 | 主要新增架构能力 | 不做什么 | 验证指标 |
| ---: | --- | --- | --- | --- | --- | --- |
| 1 | 课程目标 → 课程对象 | 目标 → 可审教课程方案包 → 教师确认 → 课程/单元/活动草稿回执 | 模拟 ClassIn 机构、课程结构、方案包 Artifact、审教、审批、写回和评价事件 | 统一 Run/Context/Artifact/Review/Action/Receipt 状态骨架 | 不生产 PPT 文件，不接真实 ClassIn，不做正式发布 | 目标确认时间、审教轮次、意见解决率、教师修改距离、保存成功/冲突/拒绝可追踪 |
| 2 | 作业批改 → 错因分析 → 订正 | 作业结果 → 错因候选 → 订正练习 → 学生完成 → 复查 | 老师侧批改与错误聚类，学生侧提示/订正，结果回到证据 | 学生作业数据、评分标准、分层练习、答案保护和二次结果 | 不自动改正式分数，不跨班自主执行 | 批改时长、订正完成率、二次正确率、独立作答率 |
| 3 | 备课演练 → 教学改进 | 演练证据 → 时间戳反馈 → 课件/活动修订 → 复练对比 | 固定媒体样本、可观察指标、Artifact 版本和前后比较 | 媒体证据、时间戳、版本差异、证据口径和隐私治理 | 不做教师绩效评分，不把声学指标当能力事实 | 反馈采纳率、复练率、前后证据变化、教师准确性评价 |
| 4 | 学情诊断 → 个性化干预 | 多源学习证据 → 诊断假设 → 计划 → 待办/练习/消息草稿 → 复查 | 先做 Copilot 计划和逐项审批，验证有限 Agent 所需运行记录 | 多对象计划、白名单工具、审批、部分成功、复查和撤销 | 不自动推断因果，不自动发送敏感消息，不直接改变学生事实 | 计划采纳率、按期完成率、复查改善、误发/撤销率 |

## 六、优先级判定规则

- **战略业务优先级**：诊断 → 个性化干预、作业 → 订正、备课演练 → 教学改进；它们直接承接学生结果和教师改进。
- **工程实施顺序**：课程目标 → 课程对象、作业 → 订正、备课演练 → 教学改进、诊断 → 个性化干预。
- **升级为有限 Agent 的条件**：至少两个真实业务 Tool、可见计划、持久 Run、审批门、失败恢复、审计和结果复查同时成立；否则保持工具或 Copilot。
- **任何阶段的红线**：成绩、提交状态、课堂事实、权限和正式发布状态不能由模型直接改写；所有业务写回先形成 `ProposedAction`，再经审批和领域校验。
