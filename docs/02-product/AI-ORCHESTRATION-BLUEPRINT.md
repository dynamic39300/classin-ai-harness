# 教师 WorkBuddy AI 编排蓝图

## 文档定位

本文沉淀关于教师 WorkBuddy 下一阶段推进方式的讨论结论，重点回答：

1. 教师工作台涉及哪些核心业务场景；
2. 每个场景由哪些 AI 能力、Skill、业务数据和 Domain Knowledge 共同完成；
3. 教师如何在前端理解、编辑、确认和追踪这条 AI 流程；
4. 产品经理应该如何拆解和设计这套 AI Orchestration。

本文是产品层的 `RECOMMENDATION` 和设计基线，不新增或修改 `docs/00-project/DECISION-LEDGER.md` 中的 `LOCKED` 决策。后续如果需要把本文中的建议升级为项目事实，应先补充证据、影响和用户确认状态。

## 一、当前共识

### 1. 终局产品

终局产品是一套通用教师 WorkBuddy，也就是面向教师完整教学工作的 AI 工作台。

教师不需要理解或选择内部的 Agent、Skill、MCP、模型或工具。教师只需要说明希望完成的教学结果，WorkBuddy 负责组织上下文、证据、知识、产物和后续行动。

ClassIn 不是 WorkBuddy 能否成立的唯一前提，而是最强的上下文、执行和结果反馈增强层。未连接 ClassIn 时，教师可以通过手动输入、资料上传和外部连接器完成核心工作；连接 ClassIn 后，WorkBuddy 可以在授权范围内获得更连续的课程、课堂、作业、互动和结果证据。

这一点与当前项目简报和 D-001 的统一工作台决策一致：

- 产品入口是统一教师 WorkBuddy 工作台；
- AI 工具、Copilot 和 Agent 是实现层能力，不是教师的产品导航；
- 产品按教学结果和业务时刻组织，不按 Agent 人格或模型能力组织。

### 2. 当前更重要的问题

当前不应把主要精力放在建设一个通用的底层 Agent 平台。底层 Runtime、模型路由、MCP、A2A 和多 Agent 协作属于实现层问题，必须服务于真实教师场景。

当前最需要明确的是整条 AI 实现链路：

- 前端需要提供什么样的教师体验和控制点；
- 每个场景需要哪些可复用 Skill 资产；
- AI 如何经过一组可理解、可恢复的步骤完成任务；
- 需要接入哪些业务事实和业务工具；
- 需要积累哪些 Domain Knowledge；
- 最终如何进入课程、作业、资源、待办、消息和教学结果等业务对象。

因此，下一阶段的核心产物应该是 **AI Orchestration Blueprint**，而不是更多 Agent 数量或更复杂的 Agent 拓扑。

## 二、产品经理要设计的七个 Module

这里使用 Module、Interface、Seam、Adapter、Depth、Leverage 和 Locality 作为统一设计语言。产品经理不需要提前决定所有技术实现，但必须把每个 Module 的责任、输入、输出、控制点和失败方式说明清楚。

### 1. 业务场景 Module

描述教师在什么业务时刻，要完成什么可观察的教学结果，涉及哪些真实业务对象。

它不等于页面列表，也不等于 AI 功能列表。一个业务场景可能跨越课程、课堂、作业、待办和消息多个页面。

### 2. AI 编排 Module

描述教师目标如何经过一系列步骤完成，包括目标澄清、上下文装配、知识检索、Skill 执行、校验、教师确认、业务写回和结果复查。

它是本蓝图的核心 Module。它应隐藏流程分支、重试、降级、人工等待和结果判断的复杂性，为前端提供一个可理解的任务状态 Interface。

### 3. Skill 资产 Module

描述每个可复用的教学方法能力，例如目标澄清、课程结构生成、资源选择、备课反馈、批改、错误聚类和干预计划生成。

Skill 不拥有课程、学生、权限或正式业务状态，也不能直接写入业务系统。它负责方法、结构化输入输出、知识使用方式、结果校验和降级策略。

### 4. Context / Data Module

描述 AI 在当前身份、机构、课程、班级、学生和时间范围内可以读取哪些事实和证据。

这个 Module 需要处理权限、字段最小化、数据新鲜度、对象版本、来源和缺口。它不能把所有业务数据粗暴地拼接成 Prompt。

### 5. Domain Knowledge Module

描述课程标准、教学法、学科知识、评分量规、机构规则、沟通规范和教师偏好如何进入 AI 流程。

Domain Knowledge 提供判断依据，但不拥有当前课程状态、权限和执行结果。

### 6. Teacher Experience Module

描述教师如何表达目标、查看上下文、编辑产物、理解依据、审批动作、处理失败和查看复查结果。

它不是 AI 编排的装饰层，而是将内部复杂性转化为教师可理解控制的主要 Module。

### 7. Evaluation Module

描述如何判断一次 AI 协作是否真正帮助教师完成了业务结果，包括产物质量、教师采纳、修改距离、执行成功、后续使用和教学结果。

模型是否返回内容、调用是否成功或对话是否结束，都不能单独代表业务完成。

## 三、教师业务链条与 AI 能力分布

教师 WorkBuddy 应沿完整教学循环组织业务场景。AI 能力覆盖不只是一组单点工具，还包括围绕业务对象的组合能力和对业务结果负责的完整闭环。

### 3.1 三层能力覆盖

| 能力层级 | 作用 | 典型输出 | 默认产品形态 |
| --- | --- | --- | --- |
| 单点能力 | 完成一次生成、识别、转换、检索、解释或检查 | 摘要、题目、转写、检查报告 | AI Tool |
| 组合能力 | 多个 Skill、Tool 和规则校验围绕一个业务对象协作 | 可编辑 Artifact、判断草稿、来源和不确定性 | AI Copilot |
| 完整业务闭环 | 从目标、证据和产物走到教师确认、业务写回和结果复查 | 业务对象变化、ExecutionReceipt、EvaluationEvent | Copilot；满足条件后才是有限 Agent |

### 3.2 三条核心业务结果链

WorkBuddy 的核心定位是围绕教师教学闭环建立三条结果链：

1. **作业与结果证据 → 错因分析 → 订正练习 → 学生完成与复查**；
2. **备课演练证据 → 可观察反馈 → 课件/活动改进 → 再次演练对比**；
3. **学情与课堂/作业证据 → 诊断假设 → 个性化干预 → 结果复查**。

“课程目标 → 课程对象”是课程生产基础链和当前锁定的第一条工程样板，为上述三条结果链提供目标、内容、活动和评价标准等上游结构。

| 业务域 | 教师要完成的结果 | 代表性 AI 能力 | 推荐 AI 形态 |
| --- | --- | --- | --- |
| 目标与课程设计 | 把标准、目标和班级特点变成可执行课程 | 目标澄清、标准对齐、课程结构、活动设计 | Tool / Copilot |
| 内容与备课准备 | 形成真正可以使用的教案、课件和活动 | 资源检索、课件生成、出题、备课检查、演练反馈 | Tool / Copilot |
| 课堂与教学实施 | 降低记录和即时处理成本 | 字幕、板书整理、课堂摘要、互动提示 | Tool / Copilot |
| 评价与教学诊断 | 从作业和课堂证据形成可解释判断 | 批改、错误聚类、证据摘要、诊断假设 | Copilot |
| 干预与协同服务 | 把判断转化为分层行动和沟通 | 订正练习、资源包、待办、消息草稿、复查计划 | Copilot；Agent 候选 |
| 反思与持续改进 | 把结果带入下一轮教学 | 目标复盘、策略比较、资源复用、下一轮计划 | Copilot；长期跟踪 Agent 候选 |

这些业务域不是六个孤立产品频道。目标、课程、班级、学生、产物、证据和结果会跨域流动，AI 编排需要保持这些对象之间的连续关系。

## 四、统一 AI 编排主链

所有业务场景都可以先映射到以下共同主链：

```text
教师目标
→ 范围与成功标准
→ 身份、权限与上下文确认
→ 业务事实与证据读取
→ Domain Knowledge 检索
→ Skill / Tool 执行
→ Artifact 或判断草稿
→ 规则校验与证据检查
→ 教师编辑、确认或拒绝
→ ProposedAction
→ 业务对象写回
→ ExecutionReceipt
→ 结果复查与评价
→ 下一轮教学调整
```

每个场景不一定需要完整执行所有步骤，但必须说明哪些步骤被跳过，以及为什么可以跳过。

### 每一步的产品问题

| 步骤 | 产品经理需要明确的问题 |
| --- | --- |
| 目标与范围 | 什么情况下必须追问，什么情况下可以开始生成？ |
| 上下文确认 | 教师是否知道系统使用了哪些资料和业务范围？ |
| 证据读取 | 事实、证据、推断和缺口是否分别表达？ |
| 知识检索 | 哪些建议需要课程标准、教法或机构规则支撑？ |
| Skill 执行 | 这是单点工具、可复用方法还是跨对象任务？ |
| 产物生成 | 输出是文本、结构化 Artifact、判断假设还是待确认动作？ |
| 校验 | 哪些问题由规则判断，哪些问题需要教师判断？ |
| 教师控制 | 哪些字段可以编辑，哪些动作需要批准，哪些动作禁止自动化？ |
| 写回执行 | 修改哪个业务对象，影响什么范围，能否撤销？ |
| 结果复查 | 什么证据能证明任务真正完成或需要调整？ |

## 五、Pipeline、Copilot 与 Agent 的选择原则

建议默认采用“固定业务流程 + 有限 AI 选择 + 明确教师控制点”，而不是首先建设开放式多 Agent 网络。

| 场景特征 | 推荐实现形态 | 判断依据 |
| --- | --- | --- |
| 步骤固定、规则明确、无跨对象规划 | 确定性 Pipeline | 重点是可重复、可解释和易评价 |
| 需要读取当前对象并给出草稿 | Copilot 流程 | AI 辅助判断，教师确认后继续 |
| 需要从多个 Skill 中选择少量步骤 | Orchestrator + Skill | 允许有限动态选择，但范围受控 |
| 跨多个业务对象、持续运行、等待和复查 | 有限 Agent | 需要持久 Run、计划、审批、回执和恢复 |
| 正式评分、敏感学生判断、外部沟通、正式发布 | 人在回路 | 不把专业责任转移给模型 |

单次模型调用、两次模型调用或多个 Skill 串联，本身都不足以成为 Agent 的理由。

### 代表性对比

“课程目标 → 课程对象”适合先采用：

```text
目标澄清 Skill
→ 课程结构 Skill
→ 可审教课程方案包初稿
→ 教师审教与意见处理
→ 方案包修订版本
→ 规则校验
→ 最终确认
→ 保存课程/单元/活动草稿
```

第一版不生产具体 PPT 文件。PPT 课件 Artifact 从最终确认的课程方案包派生，属于第二版扩展。

“诊断 → 干预计划 → 创建练习 → 创建待办 → 发消息 → 复查”才具备有限 Agent 的候选特征，因为它跨越多个业务对象、拥有持续时间并需要跟踪结果。

## 六、前端体验设计重点

WorkBuddy 的前端特色不应只是更大的聊天框，而应是让教师看懂和控制 AI 工作过程。

### 1. 目标区

教师说明希望完成的教学结果，WorkBuddy 帮助补齐对象范围、时间、约束和成功标准。

### 2. 上下文与证据区

教师可以看到使用了哪些课程、班级、作业、资料、知识来源和时间范围，也能看到哪些信息缺失或未经授权。

### 3. 产物工作区

AI 输出必须成为可编辑、可比较、可恢复的教学产物，而不是只能在聊天记录中查看的内容。

### 4. 计划与控制区

教师能够看到接下来会做什么、哪些步骤正在等待、哪些动作会影响业务对象，以及如何暂停、修改、拒绝或重试。

### 5. 执行与复查区

教师能够看到对象差异、风险、审批范围、实际回执、失败项、撤销能力和下一步复查。

产品承载原则是：对话负责目标协调，结构化区域负责产物，证据区域负责可信度，控制区域负责副作用，复查区域负责结果闭环。教师不需要看到内部 Agent、Skill 或 Harness 拓扑。

## 七、Skill 资产建设原则

Skill 不应只是 Prompt。每个 Skill 都应形成可复用、可测试和可评价的资产。

### Skill 最小契约

```text
Skill
  purpose / nonGoals
  inputSchema / outputSchema
  contextRequirements
  knowledgeRequirements
  executionSteps
  validationRules
  evidenceBehavior
  failureModes
  downgradeStrategy
  sideEffectClass
  evaluationContract
  owner / version / truthLabel
```

### 建议的 Skill 建设顺序

1. `course-goal-clarification`：目标、范围、成功标准和缺口；
2. `course-structure-drafting`：课程、单元和活动结构；
3. `course-artifact-revision`：根据教师修改形成新版本和差异；
4. `resource-selection`：在权限和版权范围内选择资源；
5. `lesson-rehearsal-feedback`：基于可观察演练证据生成改进建议；
6. `submission-review`：形成批改或反馈草稿；
7. `error-clustering`：聚类共性错误并保留证据；
8. `diagnosis-hypothesis`：形成可确认、可过期的诊断假设；
9. `intervention-plan-drafting`：形成干预计划和复查节点；
10. `communication-draft`：形成待确认的沟通草稿。

首期不需要把每个 Skill 包装成专业子 Agent。多个 Skill 可以由同一个主 Run 编排，只有在子任务拥有独立目标、受限上下文、独立生命周期和失败恢复时，才考虑增加专业子 Agent。

## 八、业务数据与 Context 设计

业务数据不是给模型的原始资料堆，而是按任务授权、按最小范围装配的 Context Pack。

### 业务数据至少需要回答

- 当前教师属于哪个机构、拥有哪个角色；
- 当前任务涉及哪个班级、课程、学生和时间范围；
- 当前业务对象的稳定 ID、版本和状态是什么；
- 教师可以读取和修改什么；
- 数据的来源、更新时间和缺口是什么；
- 动作执行后由哪个事实所有者返回结果。

### 四条代表性闭环的最小 Context Pack

| 纵向闭环 | 最小上下文 | 缺失时降级 |
| --- | --- | --- |
| 课程目标到课程对象 | 教师范围、目标、课程结构、授权资料、课程标准 | 从空白课程生成草稿并标记来源有限 |
| 备课演练到改进 | 目标、教案/课件、演练素材、时间戳和反馈维度 | 只做转写或一般表达建议 |
| 批改到订正 | 作业、提交、评分标准、反馈、课程目标和订正状态 | 只摘要作答，不给正式评分建议 |
| 诊断到个性化干预 | 目标、获授权学习证据、机构规则、资源、待办和消息权限 | 只展示证据摘要，不生成学生结论或外部动作 |

所有业务读取工具都应返回来源、版本、时间、权限范围和标准错误。业务事实、教学证据和 AI 推断不能混在同一个无来源的上下文对象里。

## 九、Domain Knowledge 资产建设

Domain Knowledge 负责“什么是合理的教学判断和产物”，不负责证明对象已经保存或教师有权限执行。

### 首批知识资产

- 课程标准和学段目标；
- 学科知识结构和先修关系；
- 单元与活动设计方法；
- 评分量规、成功标准和反馈规范；
- 机构课程设计规则；
- 未成年人保护、敏感判断和沟通规范；
- 教师确认过的模板和个人偏好。

### 知识资产最小契约

```text
KnowledgePack
  source / owner / version
  subject / grade / scope
  effectiveAt / expiresAt
  retrievalUnits
  citationRequirements
  conflictRules
  evaluationSet
  truthLabel
```

未经教师确认的诊断假设不能进入长期业务记忆；学生事实、教师推断、机构规则和个人偏好必须分开治理。

## 十、场景编排卡

每个业务场景统一使用下面的产品拆解卡，避免只描述页面或只描述模型能力。

```text
场景名称
教师目标
触发入口
成功结果
涉及业务对象
用户与权限范围
需要读取的业务数据
需要检索的 Domain Knowledge
Skill / Tool 链
生成的 Artifact 或判断
规则校验
教师控制点
ProposedAction
写回对象
ExecutionReceipt
失败、恢复和降级
评价指标
当前证据等级
```

每张卡都必须能够回答：教师发出了什么意图、四类输入由谁拥有、哪一步产生副作用、哪个 Interface 是可替换 Seam、失败时保留什么、哪个事件证明业务结果发生。

## 十一、四条优先工程纵向切片

### 1. 课程目标 → 课程对象

当前已锁定的第一条切片，业务名称就是“课程目标 → 课程对象”，不把 `EDU-01` 作为教师侧场景名称。它重点验证：

- 目标澄清；
- 课程上下文；
- 课程、单元、活动 Artifact；
- 教师编辑和差异；
- 草稿保存、版本冲突和回执；
- 评价事件。

它是最适合用来建立场景编排卡和前端状态样板的第一条链路。

### 2. 作业批改 → 错因分析 → 订正

重点验证作业、提交、评分标准、错误聚类、反馈草稿、分层订正练习和二次结果证据。正式分数和提交状态仍归业务系统和教师确认所有。

### 3. 备课演练 → 教学改进

重点验证媒体或演练证据、时间戳、可观察反馈、版本比较和个人改进计划。它不应直接成为教师绩效判断。

### 4. 学情诊断 → 个性化干预

重点验证证据、诊断假设、教师确认结论、干预计划、作业/待办/资源/消息草稿和复查。它是最适合检验有限 Agent 的场景，但不应作为第一条工程切片。

这四条场景的作用不是同时实现，而是形成对照：第一条验证课程产物和统一状态骨架，第二条验证学生数据、答案保护和反馈结果，第三条验证媒体证据与 Artifact 版本，第四条验证跨对象计划、审批、部分成功和复查。

## 十二、下一阶段推进顺序

### 阶段 A：形成 AI 编排蓝图

产出：业务时刻地图、统一主链、四条场景编排卡、Skill 清单、数据矩阵、知识资产清单、前端状态矩阵和评价指标。

完成条件：每条场景都能从教师目标追踪到 Artifact、教师控制、业务动作和结果复查；未验证生产能力被标记为 `UNKNOWN`、`SIMULATED` 或 `FUTURE`。

### 阶段 B：做四条场景的横向比较

比较四条场景中重复出现的 Module、Interface、Seam、Adapter 和控制能力，判断哪些应该成为 WorkBuddy 共享能力，哪些只属于特定业务域。

完成条件：共享 Module 具有真实 Leverage；删除它后，复杂性确实会在多个场景和调用方重复出现，而不是为了形式提前抽象。

### 阶段 C：选一条主切片形成产品样板

继续以“课程目标 → 课程对象”为第一条，逐步把当前界面演示替换为真实的 Scenario Orchestrator、Skill、Context Pack、Artifact、Approval、Adapter 和 Evaluation 组合。

完成条件：教师能够从目标输入走到经过审阅、审批、模拟写回、稳定回执和评价记录的完整闭环。

### 阶段 D：按工程顺序扩展四条切片

按“课程目标 → 课程对象、作业批改 → 错因分析 → 订正、备课演练 → 教学改进、学情诊断 → 个性化干预”的工程顺序扩展。每条切片都要判断哪些能力是真正共享的，哪些数据、知识和风险只属于特定场景。

在具备真实数据、权限、草稿、回执、撤销和评价证据之前，不进入开放式多 Agent 或跨机构自动执行。

## 十三、决策门

### G0：场景值得做

- 教师结果和成功标准明确；
- 业务对象和事实所有者明确；
- 最小上下文包、风险和降级路径明确；
- 存在可执行的人工基线。

### G1：数据和控制就绪

- 身份和对象级权限可验证；
- 业务对象有稳定 ID、版本和错误语义；
- 读取、草稿、审批和回执接口明确；
- 领域规则、知识来源和安全边界有负责人；
- 评价事件和退出路径已定义。

### G2：Copilot 价值成立

- 教师持续采用产物或建议；
- 相对人工基线节省时间或提高质量；
- 修改距离、拒绝原因和证据引用可以解释；
- 连续多个任务周期有正向信号。

### G3：有限 Agent 安全成立

- 计划、审批、幂等、部分成功、恢复、撤销和复查可运行；
- 权限拒绝不会被绕过；
- 高风险判断和外部沟通仍由教师控制；
- 业务回执与真实对象一致。

## 十四、明确不做的事情

当前不做：

- 先建设一个脱离业务场景的通用多 Agent 平台；
- 把每个页面、Skill 或模型包装成一个 Agent；
- 让教师选择内部 Agent、模型或 MCP；
- 把所有 ClassIn 数据复制为长期 Memory；
- 把 AI 推断直接写成学生事实、成绩或正式业务状态；
- 用 Demo 的完整流程证明真实数据、权限、质量和商业价值已经成立；
- 用模型输出数量、对话轮数或工具调用成功替代教师结果。

## 十五、当前开放问题

本文仍需要后续研究和业务确认的问题包括：

1. 第一批真实教师、学科、机构和课程范围是什么；
2. 无 ClassIn 与有 ClassIn 两种模式是否需要完全相同的核心对象模型；
3. 教师 WorkBuddy 是主要作为独立入口，还是主要作为 ClassIn 情境入口；
4. 哪些业务对象真实支持草稿、版本、幂等、撤销和逐项回执；
5. 哪些课程标准、机构规则和评分量规可以进入第一批知识资产；
6. 哪些低风险动作可以由教师预先授权，哪些动作永久需要逐次审批；
7. 诊断假设、教师确认结论和长期偏好之间如何分别存储和过期；
8. 第一条真实试点应以教师效率、产物质量还是教学结果作为主要评价目标。

## 十六、本文结论

教师 WorkBuddy 的核心竞争力不只是模型能力，而是把以下要素组合成可重复、可控制、可评价的教师工作闭环：

```text
教师业务场景
× AI 编排流程
× Skill 资产
× 业务数据与工具
× Domain Knowledge
× 教师前端控制体验
× 结果评价与复查
```

下一阶段的重点不是继续扩展 Agent 数量，而是明确每个教师业务结果由哪些 AI 步骤、Skill、数据、知识、控制点和前端状态共同完成。

当这套编排被设计清楚后，底层应该使用 Pipeline、Copilot、有限 Agent 还是其他实现方式，会从产品目标和场景约束自然推导出来。
